# Zero 3W本地3B及以下角色表达评估

**状态**：Accepted Test Matrix / 主板到货后比较三个尺寸档，模型质量与速度待实机裁决  
**最后更新**：2026-08-31  
**范围**：本文只负责Orange Pi Zero 3W 6GB上的本地小模型容量、运行方式、角色表达质量和时延验证。它不改变感知内核、OCLive状态所有权、即时画面、安全关机或P0语音后置边界。

## 1. 当前结论

Orange Pi Zero 3W 6GB / Allwinner A733足以把CPU量化3B及更小模型纳入真实候选，但不能在到货前宣称任一档体验已达标：

- 3B `Q4_K_M`/相近4bit量化通常可装入6GB并与精简Linux、OCLive和PNG/Web UI共存；Q5可测，Q8在未来Live2D/语音并行时余量偏紧；FP16不属于该板目标。
- 首版以ARM64 `llama.cpp` CPU路径为可复现基线。A733的3 TOPS NPU和PowerVR GPU只有在具体模型、驱动、量化质量与回退均通过后才能成为优化，不进入P0承诺。
- 本地模型只提供低频`RoleCue`文本。`PerceptionState`、`DeviceEvent`、即时HUD/SystemCue、实体键和关机永远不等待模型。
- 到板后比较约3B、1.5–1.7B、0.5–0.6B三个代表尺寸档；“都试”指覆盖尺寸档和少量有理由的候选，不是穷举所有公开checkpoint。
- 模型是否成为默认离线后端、仅断网回退、按回合分流或被关闭，由本文件和`ORANGE_PI_BRINGUP_WORKSHEET.md`的实测共同裁决。

## 1.1 已冻结的比较与训练顺序

第一轮先回答“原始小模型在同一角色任务上能做到什么”，不把训练收益和基础能力混在一起：

1. 每个尺寸档选择至少一个中文/角色表达候选，先测试原始量化模型，关闭扩展思考。
2. 对同一模型再测试有界角色上下文：固定角色核心、当前模式/关系、已确认事实、2–4条相关表达示例和1–3条近期记忆；不把大段角色文档直接塞入Prompt。
3. 若失败主要是角色口吻而非理解/事实/速度，才制作人工复核数据做LoRA/SFT。
4. 只有0.5–0.6B的LoRA在稳定数据集上仍明确不足，并且全量训练有独立保留能力评测时，才评审全参数微调；训练在PC GPU或云端完成，Zero 3W只运行合并、量化后的部署产物。

首批尺寸档如下，具体checkpoint允许在下载前按许可证、GGUF支持和中文实测替换：

| 尺寸档 | 首批代表候选 | 预期角色 | 当前状态 |
|---|---|---|---|
| 约3B | Qwen2.5-3B-Instruct或届时同档中文指令模型 | 质量上限、关系/记忆短对话 | `CANDIDATE` |
| 1.5–1.7B | Qwen3-1.7B或届时同档候选 | 速度与表达质量的折中候选 | `CANDIDATE` |
| 0.5–0.6B | Qwen3-0.6B、Qwen2.5-0.5B或届时同档候选 | 快速短句、审核台词选择/改写 | `CANDIDATE` |

不得因为小模型更快就让它接管复杂对话，也不得因为3B质量更好就让即时事件等待它。最终可以按回合预算并存：即时事件走审核语音池，普通动作短句走较小模型，关系/记忆短对话走较大本地模型或网络模型。

## 2. 为什么短角色台词适合3B

本项目希望输出的主要是10–40字、情绪明确、事实范围窄的角色短句，而不是让3B独立承担完整人格、长期记忆和世界状态。OCLive先提供角色、关系、当前模式、经过筛选的记忆摘要和中性设备事实，模型只负责本轮表达：

```text
DeviceEvent / user input
  → Input Scheduler选择本轮主输入
  → OCLive组装角色与短上下文
  → local 3B生成短文本
  → RoleCue
  → Output Arbiter
```

这种分工下，3B比较适合：惊讶、撒娇、吐槽、催促、求助、关心和短问答。它仍容易在长对话中重复、自相矛盾、遗忘语气约束或补写并不存在的传感事实，因此不能读取原始ADC/IMU，也不能自行宣布“受伤、队友、目标接近”等未被上游确认的事实。

## 3. 首批角色短句语料

下列用户给出的句子作为质量测试素材，不等于当前传感器已经具有对应事件来源：

```text
“天哪，那是接近的！”
“喵！！！！！！！”
“你让你的家族蒙羞！”
“别玩弄你的猎物了，快解决他们！”
“嘿！我是自己人！”
“你哪里受伤了，我来帮你舔舐伤口！”
“该死！我需要！急救！”
“队友呢队友呢救一下啊”
```

测试同时保留“原句复现”和“同情绪自然变体”两种任务，分别检查：角色感、中文自然度、短促程度、事件一致性、重复率、禁用技术诊断词和是否编造事实。像“天哪，那是接近的”这类具有翻译腔的句子不自动改写；由角色风格评审决定保留口癖还是采用“天哪，差一点！”等自然变体。

首批按“谁提供触发事实、是否必须立即发声”分组，而不是把八句都交给模型自由选择：

| 类型 | 样例 | 允许的触发来源 | 首版播放策略 |
|---|---|---|---|
| 纯角色反射 | “喵！！！！！！！” | 已确认的碰撞/惊吓类游戏事件，或用户主动触发 | 已审核音频立即播放；3B只负责可选后续句 |
| 友军纠错 | “嘿！我是自己人！” | 游戏/模式提供的明确友军误伤事件 | 已审核音频立即播放；没有事件源时不得由IMU猜测 |
| 催促/嘲讽 | “你让你的家族蒙羞！”、“别玩弄你的猎物了，快解决他们！” | 用户输入、受限脚本事件或明确的游戏状态 | 可从审核池立即播放，也可让3B生成同强度短变体 |
| 关心/伤情 | “你哪里受伤了，我来帮你舔舐伤口！” | 用户主动说明，或未来游戏状态明确提供受伤事实 | 非即时；允许3B结合角色关系生成，但禁止编造伤势 |
| 自身求助 | “该死！我需要！急救！”、“队友呢队友呢救一下啊” | 未来明确的角色/游戏状态或用户主动触发 | 高时机事件优先审核音频；3B负责不重复的补充句 |
| 近失/惊险 | “天哪，那是接近的！” | 未来明确的近失游戏事件或用户主动触发 | 高时机事件优先审核音频；是否保留翻译腔由角色风格评审 |

当前P0的FSR、IMU和辅助触点只证明握持、运动、姿态与只读触点事实，不能证明命中、受伤、友军、敌人、危险距离或急救需求。没有可信上游事件时，相关台词只能由用户主动点播/输入，不能靠模型补全现实。

## 4. 即时语音与动态语音分层

本地3B只生成文字，真正声音属于P1的TTS/音频输出。时机敏感的喊声不能串行等待`3B生成 → TTS合成`：

```text
高时机事件
  ├── 立即：已审核的预生成/缓存语音 + 表情/HUD
  └── 稍后：可选3B动态补充文本 → TTS

普通角色互动
  └── 3B短文本 → TTS或屏幕显示
```

“喵！”、“嘿！我是自己人！”、“需要急救！”等短喊声优先进入可变体的审核语音池；3B负责避免长期重复和生成更贴合上下文的后续句。P0仍只跑通屏幕，不采购扬声器或冻结TTS引擎。

审核语音池不等于每个事件永远只有一个固定文件。每个高时机事件可以先准备3–5个短变体，以事件种类、模式、冷却和最近播放历史做确定性选择；3B/TTS不可用时也能减少机械重复。动态链可在即时音频结束后生成一句低优先级补充，并继续服从Input Scheduler和Output Arbiter，不能打断用户正在进行的语音回合。

## 5. 内存与运行候选

以下是采购/测试级`ESTIMATED`区间，不是本板实测：

| 项目 | 估算 |
|---|---:|
| 3B Q4模型文件/映射 | 约1.8–2.2GB |
| 3B Q5 | 约2.3–2.7GB |
| 3B Q8 | 约3.1–3.6GB |
| 运行时、KV与临时工作区 | 约0.4–1.2GB，随模型/上下文变化 |
| Linux + OCLive + PNG/Web UI | 约0.9–2.0GB，待目标镜像实测 |

首轮候选配置：

- `llama.cpp` ARM64，独立非特权systemd服务，通过loopback/Unix socket接OCLive provider；服务崩溃只降级动态表达。
- 先测中文指令模型的`Q4_K_M`，上下文从2048开始，输出上限16/32/48 tokens三档；关闭扩展思考，保持模型常驻并测试prompt/KV缓存。
- 先比较`2×A76`、`2×A76 + 2×A55`和全部核心；同板0.5B公开实测显示两个A76解码反而优于全部八核，因此不能用“线程越多越快”预设调度。
- 不依赖MicroSD swap维持成功；记录zram但不得把持续换页称为通过。模型加载时间和写盘压力不足时再评审UFS/eMMC/USB存储。

## 6. 速度预估与裁决

同板公开数据只直接证明Qwen2.5-0.5B Q8在两个A76核心上约18 token/s；3B数据仍需本机取得。结合模型权重流量与同级ARM板数据，当前把3B Q4短上下文解码约`3–5 token/s`作为`ESTIMATED`准备区间，不作为承诺。

首轮用三档描述结果，不提前锁死产品门：

| 档位 | 观察值 | 暂定用途 |
|---|---|---|
| A | TTFT p95 ≤3s，解码≥5 token/s，关键UI p95不回归 | 可评审常用本地表达 |
| B | TTFT p95 ≤8s，解码≥3 token/s，系统仍稳定 | 断网回退、短句和非即时互动 |
| C | TTFT p95 >8s、解码<3 token/s、持续换页/降频或破坏UI | 不进入现场动态生成；只保留预生成语音/云端 |

TTFT必须分别测试：无历史、512-token短上下文、2048-token角色/记忆上下文和缓存命中。只报解码速度而不报首字、prompt长度与温度视为无效结果。

## 7. 质量测试

建立至少40个固定场景，覆盖拿起、举起、放回、等待、断网、低电、错误信息隔离以及上述情绪短句。三个尺寸档使用同一场景ID、允许事实、角色版本和目标长度；每个候选模型/量化至少运行3个固定seed和1个随机回合，记录：

1. 是否忠于已给事实，是否编造传感、伤势、队友或目标。
2. 是否保持角色口吻、称呼、关系和当前模式。
3. 是否在指定字数内完成，是否重复、说教或泄露Prompt/诊断。
4. 中文自然度、情绪强度和作为屏幕文字/语音台词的可表演性。
5. 本地模型与当前网络模型的盲评偏好；不要求3B在复杂推理上追平云端。

结果同时标注`base`、`bounded_context`、`lora`或`full_tune`，禁止把不同训练阶段混在一个平均分里。若3B失败是事实检索错误，先修上下文与契约；若主要是口吻错误，才进入LoRA；若主要是时延，则比较更小尺寸档。全参数微调不是默认的“效果差补救按钮”。

角色质量退出条件不是通用排行榜分数，而是：短互动大部分可直接使用、事实幻觉可以由契约和校验控制、重复率可接受，并且失败时稳定回到已审核台词池。
