# 主机侧娱乐后端：屏幕打靶与投影靶场（设计基线）

**状态**：CANDIDATE（2026-09-23；项目所有者提出「结合电脑做空枪打靶、投影靶场、参考游戏做靶场交互与 wargame 特色」的方向，尚未裁决）  
**唯一职责**：定义「以 PC 为主机时的**娱乐性打靶 / 靶场 / 投影模拟**」这一方向的目标、架构定位、瞄准通道选型、延迟归属、枪侧改动量、玩法范围、安全与文案红线、分阶段路线与待决项。  
**不负责**：感知契约字段（以 `ailive-gun-spirit-contracts` 为准）、角色表达与人格（OCLive 兄弟仓）、投影仪/相机采购细节（采购核对清单）。  
**上游**：`DECISIONS.md` 的 ADR-063 / ADR-066 · `ESP32_GUN_ASSISTANT.md` · `PROJECT_BOUNDARIES.md` · `PROJECT_BASELINE.md`  
**下游**：`ROADMAP.md`（**须独立立项，不进入器灵核心**）· `test-worksheets/采购核对清单.md` · `PROJECT_BOUNDARIES.md` §4（**仅在 ADR-066 升为 ACCEPTED 后才新增行**）

---

## 1. 一句话目标

**枪不再只是「被聊天的对象」，而是屏幕上娱乐内容的输入设备**：空枪对着 PC 显示器或投影幕打靶，枪娘从「陪聊」变成「陪你打靶的搭档」。全部游戏逻辑与算力在 PC；**枪侧硬件零改动**，只多一个「模式位」。

## 2. 架构定位：这是**新的输出消费者**，不是新感知

```
传感器 → PerceptionState → DeviceEvent ─┬─→ OCLive（角色表达）
                                        └─→ 娱乐后端（打靶/靶场/计分）  ← 新增
                                                     ↓
                                              Output Arbiter
```

三条纪律：

1. **游戏后端与 OCLive 并列，互不写入。** 游戏数值不直接变成角色台词（避免「报分机器人」）；角色表达仍只由 OCLive 出。
2. **命中和得分属「游戏事实」，必须有独立 provenance，不得冒充感知事实。** `PROJECT_BOUNDARIES.md` §6 已写死：FSR / IMU / 辅助触点**不证明击发、命中、伤势、目标或危险距离**。游戏层的「命中」是画面几何判定结果，与感知内核无关。
3. **`control.primary.engaged` 只证明「触点状态」。** 游戏把它当作**开火输入**是游戏语义，不是物理声明；内核与契约文档中不得改称「击发」。

## 3. 瞄准通道：三案对比（核心选型）

| 方案 | 原理 | 精度 | 漂移 | 成本 | 门槛 |
|---|---|---|---|---|---|
| **A　IMU 相对指向** | 校准后按姿态把指向映射到屏面 | 差（方位角尤其差，磁干扰 + 积分漂移） | **有**，需频繁回中 | 0 元（IMU 已有） | 低 |
| **B　主机摄像头 + 枪上标记（推荐）** | PC 摄像头识别枪上刚性标记阵列 → PnP → 屏幕坐标 | 好：标记阵列 15–20 cm、2 m 距离、1080p ≈ 落点 **2–5 cm**（`ESTIMATED`） | **无**（绝对参考） | 0–40 元 | 相机通道（P1，需 ADR） |
| **C　不瞄屏幕的节奏玩法** | 只做「扣扳机时机 + 换弹速度」的反应/节奏玩法 | — | 无 | 0 元 | 低 |

**阶梯（按成本递增，每步都能单独交付价值）**：**C（0 元，先验证「扣扳机 → 画面反馈」）→ B（打印 ArUco 标贴贴枪上，0 元验证闭环）→ B+（4 灯刚性阵列，20–40 元，提升精度与抗遮挡）**。A 只作为「无相机」时的降级方案，且必须接受体验明显更差。

### 3.1 允许与禁止的分界线（**一句话规则**）

> **「瞄准射线 × 屏幕平面」求交是允许的；任何引入弹道、初速、飞行时间、下坠、风偏、命中概率或自动修正的计算都是禁止的。**

- 界面上称**准星 / 光点**，**不称「弹着点」**；
- **禁止任何形式的辅助瞄准、吸附、命中修正、后坐补偿**——可以**测量**玩家瞄向哪里，**不可以修正**它；
- 游戏层只做「射线与靶面是否相交」的判定，不做投射物动力学。

## 4. 延迟归属（本方向最关键的结构性结论）

**瞄准闭环在主机视觉内闭合，不经过枪 → PC 链路**，因此 ADR-063 的「事件到画面 p95 ≤ 100 ms」门**不适用于瞄准**：

| 环节 | 数量级 | 说明 |
|---|---|---|
| 相机采集 | 33 ms（30 fps）/ 16.7 ms（60 fps） | `ESTIMATED` |
| 标记检测 + PnP | 5–10 ms @1080p | `ESTIMATED`，用 OpenCV 几何解算，非 ML |
| 渲染 | 16.7 ms @60 fps | — |
| **motion-to-photon 合计** | **约 50–60 ms（30 fps 相机）/ 约 33 ms（60 fps）** | `ESTIMATED`，需实测 |

**枪 → PC 链路只承载离散事件**（扣扳机、换弹、举枪/放下），它们对 100 ms 级延迟不敏感。

**推论：游戏模式恰好是有线场景。** 桌面打靶用 **USB-CDC**，扣扳机延迟毫秒级——D1 的选择在游戏模式下同样正确；Wi-Fi 只在「隔房间 / 投影大屏」时使用，其 p95 仍是 `UNKNOWN`，需实测。枪侧屏的角色反馈继续容忍 100 ms，**且不参与命中判定**。

## 5. 枪侧零改动 + 模式位扩展

- 模式从双态扩为**三态**：**自由聊天 / 靶场游戏 / 离线预设**（扩展 `ESP32_GUN_ASSISTANT.md` §3）。
- 下行仍是 `AssetRef` + 短文本 + 状态位 + 模式；靶场模式新增的「得分 / 弹药 / 命中提示」只是**状态位扩展**，不引入新下行类型（若引入，须走能力协商）。
- 枪侧屏在靶场模式只显示**枪娘表情 + 极简状态位**，**不作为游戏主画面**——主画面在 PC/投影，避免小屏抢戏，也避免把 4.6 MB/s 的像素流塞进无线链路。

## 6. 玩法范围（参考游戏，娱乐向）

| 玩法 | 依赖 | 备注 |
|---|---|---|
| 计分、连击、关卡、挑战、成就 | 主机本地 | 参考街机光枪游戏 |
| 反应时间、命中率 | 同上 | — |
| **换弹速度成为玩法机制** | P1 只读换弹扩展（`MAGAZINE_AMMO_ESTIMATION.md`） | 把已有的只读扩展变成玩法价值；仍需新契约版本/能力协商 |
| 枪娘三种娱乐人格：搭档 / 解说 / 吐槽 | OCLive | 角色表达与游戏数值解耦 |
| 靶场道具：气球、罐子、飞盘、靶纸 | 主机本地 | **不模拟弹道**，只判射线与靶面相交 |
| 举枪 / 放下 → 进入 / 退出瞄准姿态 | IMU 姿态（v0.2 闭集内） | 握持 → 「人在手里」 |
| **投影靶场**（墙面/幕布大画面） | 投影仪 | **投影只是主机侧显示后端的一个选项，不引入任何新契约** |

## 7. 安全与文案红线（**必须在 ADR 中写死**）

**安全仪式（同时是角色设定）**：进入靶场模式前，枪侧屏与 PC 依次确认 **① 空仓（无弹匣、无弹）② 前方无人 ③ 不在有实弹的场所**。把确认做成**角色的仪式化行为**（「先让我检查一下」），既满足安全要求，又自然融入体验。

- 载体仅限**玩具 / 模型载体**（RADIAN MODEL 1 水弹或软气枪级），**不得与真枪配合**；
- 只在封闭空间使用；不得指向窗户、门、走道方向；
- **禁止清单**：弹道 / 初速 / 风偏 / 下坠 / 命中概率 / 射击解算；任何形式的辅助瞄准、吸附、命中修正；目标检测、目标跟踪、人体识别；把成绩用于训练或军警用途；产品文案出现「射击训练 / 战术训练 / 军警」字样。
- **对外定位**：**娱乐性打靶游戏**（与消费级光枪游戏同类），**不使用「训练」作为产品定位**。
- **相机隐私边界**：画面**只用于几何解算**，不存储、不上传、不送模型、不进角色记忆；只把「屏幕坐标 / 命中结果」这类语义量交给游戏层与 OCLive。此条与「原始采样只在节点/驱动层处理」同一逻辑。

## 8. 分阶段路线

| 阶段 | 内容 | 依赖 | 成本 |
|---|---|---|---|
| **G0** | 屏幕打靶最小闭环：扣扳机 → PC 画面反馈（方案 C，无相机、无瞄准） | 扳机触点（外部只读）+ USB-CDC | 0–20 元 |
| **G1** | 摄像头标记追踪、准星跟随（先用打印 ArUco 标贴） | P1 相机能力门 + ADR | 0 元 |
| **G2** | 四灯阵列 + 计分 / 连击 / 关卡 + 枪娘解说 | 同上 | 20–40 元 |
| **G3** | 投影靶场（大画面） | 投影仪 | 300–3000 元（可后置或借用） |

**G0 是性价比最高的一步**：它不需要相机、不需要瞄准通道，就能回答「枪当游戏输入设备好不好玩」这个最关键的问题。

## 9. 待决项

1. **扳机检测的机械方案（阻塞 G0）**：① 护圈外侧微动开关由扳机刃推动；② 护圈外侧霍尔 + 扳机贴小磁铁（非接触）；③ **完全不碰枪**——握把上加按键（街机式「开火键」）。三者都**不进入发射器内部、不连接原火控/电机/供弹**，因此不触发 `PROJECT_BOUNDARIES.md` §7 门 2；但它是**新增用途**（游戏开火判定），仍须 ADR 明确「外部、只读、非侵入」。方案 ③ 零机械风险但真实感最差。
2. **相机通道的立项与能力门**：P1 相机原定位是「娱乐观察」，现在要扩为「**瞄准通道**」——二者是同一条相机通道还是两条，须由 ADR 与 capability 命名裁决。
3. **相机型号与安装**：普通 PC 摄像头即可起步；**用可见光标记可免去 IR-cut 改造**（普通摄像头自带 IR 滤光片，IR LED 方案需拆滤光片或无 IR-cut 模块）。
4. **是否投影立项**：成本 + 场地（需暗环境、平整幕面）决定 G3 时机。
5. **娱乐后端的落地形态**：建议**先作为 `ailive-gun-spirit-host` 内的独立模块**（不进感知内核、不依赖 OCLive 内部对象），**不急于新增第 4 个 crate**——workspace 成员数有门禁断言（`GS-BOUNDARY-001`），新增 crate 必须同时显式更新该门禁与依赖 allowlist。
6. **若本方向被接受**（升格动作）：ADR-066 由 `CANDIDATE` 升为 `ACCEPTED`；`PROJECT_BOUNDARIES.md` §4 新增「游戏/模拟」行并更新「最后核对」；`ROADMAP.md` 按「**必须独立立项、不进入器灵核心**」加条目；`采购核对清单.md` 增相机 / 投影对应行；同步 `ESP32_GUN_ASSISTANT.md` §3 的三态模式。
