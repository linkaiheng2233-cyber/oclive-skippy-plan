# P0-A 软件实现设计（一体化板 + PC 宿主）

**状态**：`CANDIDATE`（2026-11-13；与 ADR-069 一致，具体接口待 CP1b/CP2 实测后冻结）
**唯一职责**：定义 P0-A 的**软件分层、任务与时钟、消息语义的分阶段落地、降级行为与验收映射**。
**不负责**：交互与界面规范（见 `FRONTEND_DESIGN_BRIEF.md` §9）· 传感器选型（见 `SENSOR_OPTIONS.md` §P0-A）· 供电（见 `MAIN_POWER.md` §P0-A）· 契约字段（以 `crates/ailive-gun-spirit-contracts` 为真源）

---

## 1. 现状与目标

| 项 | 现状 |
|---|---|
| 板上固件 | Arduino-ESP32 3.0.2 + LVGL 8.3.11，ASCII 串口协议；**已实测**点屏、触摸、7 张表情切换、双向联调（`STATE`→换图、触屏→`TOUCH`/`MOOD`） |
| 感知内核 | Rust v0.3，桌面通过 9 帧 golden；**已证可在 `no_std + alloc` 下编译且输出逐字节相同**（CP1） |
| 板上感知 | **尚未运行**。ADR-069 要求内核跑在板上 |
| 联机 | **尚未实现**。目标：USB 先通，再走 Wi-Fi STA |

**目标（P0-A 闭集）**：板端采样→本地内核融合→即时表情反馈；PC 收状态与事件、下发表达；断连时板端继续本地预设。

## 2. 分层

```
┌─ drivers ────────────────────────────────────────────┐
│ IMU(I²C)  FSR(ADC1)  霍尔(GPIO)  显示(QSPI)  触摸(I²C)  │
└──────────────────────┬───────────────────────────────┘
                       │ 节点侧滤波/去抖/去零偏
┌─ perception（Rust，单一实现）────────────────────────┐
│ SensorObservation → PerceptionReducer → PerceptionState │
│                                    └→ DeviceEvent        │
└──────────────────────┬───────────────────────────────┘
                       │ 状态快照(~1 Hz) + 变化事件(边沿)
┌─ expression（板端即时反馈）───┐   ┌─ comms ────────────┐
│ 优先级/驻留/防抖 → 表情 ID     │   │ USB-CDC 与 TCP 同语义│
└──────────────┬───────────────┘   └─────────┬──────────┘
               │ 只改「当前表情 ID」            │
┌──────────────▼─────────────────────────────▼──────────┐
│ ui（LVGL）：RoleStage + StatusBar + SystemOverlay       │
└────────────────────────────────────────────────────────┘
```

**三条纪律**：
1. **内核只有一份实现**——板上与桌面跑同一套 Rust 代码（CP1 已证等价），不得用 C++ 重写一份状态机。
2. **表情只有一个当前值**——三条通路（触屏/PC/感知）都只改它（见交互方案 §9.2）。
3. **即时反馈不等待 PC**——板端自己出图；PC 的角色回合后到可覆盖。

## 3. 任务、时钟与并发

| 任务 | 周期 | 职责 | 约束 |
|---|---|---|---|
| `sensor_task` | IMU 100–200 Hz，FSR/霍尔 20 Hz | 采样、滤波、去抖、去零偏 | 定频发送；用 `esp_timer_get_time()` 打时间戳 |
| `reducer_task` | 由观测驱动 + 1 Hz tick | 持有 `PerceptionReducer`，产出快照与事件 | **单一 `sequence` 账本**（ADR-067 §二.6） |
| `ui_task` | LVGL 30 fps | 渲染；**不直接读传感器** | 只消费有界队列里的表情指令 |
| `comms_task` | 事件驱动 | USB/TCP 收发、帧解析、心跳 | 先按类型分派，再做类型专属校验 |

- **时间**：只用单调时钟，绝不取 RTC 墙钟参与融合；PC 侧另记接收时间。
- **队列**：`sensor → reducer` 与 `reducer → ui` 都用**有界队列**；满则丢最旧并计数（不阻塞采样）。
- **显示锁**：`bsp_display_lock()` 只允许 `ui_task` 获取；感知路径**不得**碰锁（否则 100 Hz 会被渲染阻塞）。
- **`AIM` 流**（将来）：若启用，走独立账本与独立路径，**不得**进入 `PerceptionReducer`。

## 4. 消息语义分阶段

| 阶段 | 形态 | 判据 | 现状 |
|---|---|---|---|
| **S1 台架** | ASCII 行协议：`PING`/`STATE`/`STEP`/`GET STATE`/`TOUCH`/`MOOD` | 双向联调可复现 | **已通过**（2026-11-13） |
| **S2 帧协议 v1** | 二进制帧 `[magic u16][ver u8][type u8][flags u8][len u16][payload][crc16 u16]`；USB 与 TCP **同一套** | 主机可解析；截断/坏 CRC/未知 type 被拒 | 待实现（CP2） |
| **S3 正式协商** | `NodeHello`（版本+能力集）+ `AssetRef` 表达下行 | 节点可自声明能力 | 属 `GS-CONTRACT-004` |

**S2 的硬规则**（来自 ADR-067 的故障域经验）：
- 传输层**先按 `type` 分派**，再做类型专属校验；
- `STATE`/`EVENT`：严格序号（重复丢弃、倒退拒绝）；
- `AIM`：**不做连续性校验**，丢包即丢、不重传；
- 首连/重连：以**当前快照**建基线，只处理恢复后的新事件，**不重放历史**。

## 4.5 连接设计：板 ↔ 电脑 ↔ 模块（2026-11-13 补）

**三条链路，职责不重叠**：

| 链路 | 对端 | 用途 | 协议 | 发现/重连 |
|---|---|---|---|---|
| **USB-CDC** | 电脑 | 烧录、台架供电、有线联调 | 与 Wi-Fi **同一帧协议** | 无发现、无重连语义（插上即通） |
| **Wi-Fi STA** | 电脑 | 正式联机 | TCP 长连接（板主动连 PC） | UDP 广播发现 + NVS 记忆上次地址 |
| **BLE** | **仅传感器模块** | 收观测、发配对/授时 | GATT（nRF52 侧） | 白名单自动重连 |

**注意**：板**不**用 BLE 连电脑（Windows BLE 栈不稳定，D2 已定 Wi-Fi STA）。

### 4.5.1 发现与重连

```
板上电 → 读 NVS 上次地址 → 若连不上 → UDP 广播 OCLIVE_DISCOVER
        → PC 台架程序回 OCLIVE_HERE <ip>:<port> → 建立 TCP → HELLO 握手
```

- **不手填 IP**（台架可手填作为兜底）；广播端口与 TCP 端口定案前查占用。
- 断线判定 **3–5 s**（与 §5 降级一致）；恢复后**建新快照基线、不重放旧事件**。
- 心跳 1 s；连续 3 次无响应即判定断连。

### 4.5.2 射频共存（必须实测）

ESP32-S3 **单射频**：Wi-Fi STA（连 PC）+ BLE（连模块）走 `esp_coex` 分时。

| 约束 | 理由 |
|---|---|
| **固定 Wi-Fi 信道** | 共存调度与 BLE 跳频需稳定，信道漂移使丢包不可复现 |
| BLE 连接间隔不设过短 | 间隔越短，Wi-Fi 吞吐损失越大；扳机模块按 §2.3 上下文加速即可 |
| **`AIM` 高频流暂不启用** | 100 Hz 流会与 Wi-Fi 抢时隙，等实测抖动后再议 |
| 首轮必测 | Wi-Fi 吞吐、BLE 丢包、事件端到端 p95（在有/无 Wi-Fi 流量两种条件下各测一轮） |

### 4.5.3 安全（P0 口径）

局域网内明文，**不做加密**；但 `HELLO` 必须带 **NVS 配置的共享 token**（不做鉴权加密，只挡误连）。
产品化前再评估配对/密钥。**明确记录为已知风险**，不得对外宣称"安全"。

### 4.5.4 跨模块时间对齐（新发现的缺口）

每个模块有自己的单调时钟；事件只带**模块本地时间戳**。要在主机侧**跨模块排序**、并与板/PC 时钟对齐，必须做偏移估计：

| 方案 | 做法 | 精度（`ESTIMATED`） |
|---|---|---|
| **握手授时** | `HELLO`/`PING` 里带主机时间，模块记偏移；周期性（如 30 s）复测 | 单向延迟未知 → 误差 ≈ 单程延迟 |
| **往返估计**（推荐） | 主机发时间 → 模块回显自己的时间 → 用往返/2 修正偏移 | 误差 ≈ 往返抖动/2 |

- 偏移与**漂移率**（每日 ppm 级）都存 NVS，断连重连后先校一次。
- 排序原则：**同期事件按修正后时间排序；同一模块内严格按本地序号**。
- 这一条**不影响换弹/握持这类低频事件**，但影响"扣扳机时刻 vs 换弹时刻"这类组合判定 → 属玩法精度，需实测门。

## 5. 降级与失败

| 故障 | 板端行为 | PC 行为 |
|---|---|---|
| IMU 失联/超时 | 相关事实转 `unknown`，表达回 `neutral` 或 `confused` | 按 TTL 标过期，不触发角色回合 |
| FSR 未接 | 前后握保持 `unknown`（**不许伪造**） | 同上；`Ready` 永不成立（规则要求握持+姿态） |
| PC 断连（>3–5 s） | 进入**离线预设**：本地表情轮换/静止 | — |
| 链路恢复 | 建新快照基线；稳定 2–3 s 后再切回自由模式 | 只接受恢复后的事件 |
| 帧错误 | 丢弃单帧并计数；连续超限则断开 | 记录协议故障，不注入内核 |

## 5.5 运行平台（板上的"操作系统"，2026-11-13 补）

板子没有桌面 OS，所谓"操作系统"= **固件栈 + FreeRTOS 任务模型 + Flash 布局 + 内存预算**。这四项必须先定，否则后面每加一个功能都要重排。

### 5.5.1 固件栈选型

| 选项 | 现状 | 优点 | 代价 |
|---|---|---|---|
| **A. Arduino-ESP32 3.0.2 + LVGL 8.3.11** | **已验收在跑**（点屏/触摸/图库/USB 双向） | 立刻能改能验；原厂驱动现成 | 无 `std` 安全网；与 Rust 集成只能走 `no_std` 静态库；Arduino 抽象层较厚 |
| **B. 纯 ESP-IDF（C/C++）** | 未开始 | 最正统；LVGL 与 AXS15231B 都有 IDF 组件 | 要重写现有已验证的 UI 层；C 侧无契约类型 |
| **C. ESP-IDF + Rust（`esp-idf-sys`）** | 未开始 | 单一语言做业务层；可复用 `contracts`/`perception-core`（CP1 已证 `no_std`）；LVGL/驱动用现成 C 组件 | 工具链重装；需与 Arduino 的 IDF 版本解耦（见 §0.1.3 结构性提醒） |
| **D. `no_std` + embassy(esp-hal)** | 未开始 | 最轻、与模块固件同构 | **显示驱动要移植到 Rust**，工作量最大 |

**决策规则（等 CP1b 数字）**：
- 若 `no_std` 内核能作为**静态库**链进 A → **保持 A**（改动最小、风险最低）。
- 若链接不成立 → 转 **C**（保住单一语言与契约复用）。
- **B 与 D 都不作为首选**：B 丢契约类型，D 要重写显示栈。

**明确不变的一条**：无论选哪个，**感知内核只有一份 Rust 实现**，不得在板上重写第二份状态机。

### 5.5.2 内存预算（`ESTIMATED`，需实测）

| 项 | 量 | 备注 |
|---|---|---|
| 内部 SRAM | ~512 KB（其中 Wi-Fi+BLE 栈占用显著） | 任务栈、队列、堆都在这里 |
| PSRAM | 8 MB（八线） | **LVGL 帧缓冲放这里** |
| LVGL 单帧 | 480×320×2 B = **300 KB** | 双缓冲 600 KB → 必须 PSRAM |
| 立绘（7 张 260×260 RGB565） | ≈ **946 KB** | 现编在 app 里；可移 `ffat`（见 §5.5.3） |
| 余量目标 | 内部 SRAM 堆峰值留 **≥30%** | 加 BLE + 多模块后容易吃紧，必须实测 |

### 5.5.3 Flash 布局（16 MB，已实测）与**存储分层**

| 分区 | 大小 | 我们的用法 |
|---|---|---|
| `app0` | 2 MiB | **出厂程序，永久保留为恢复槽** |
| `app1` | 2 MiB | **我们的固件**（当前 1,503 KB） |
| **`ffat`** | **11.875 MiB（空）** | **内置资产区**：核心表情/字库/音效 |
| TF 卡（可选） | GB 级 | **扩展资产**：玩家自定义立绘、语音包 |
| PSRAM | 8 MB | **运行时缓存**：7 张表情仅 946 KB，可全量预读 |
| `coredump` | 64 KB | 崩溃转储 |
| `nvs` | 20 KB | 配置：PC 地址、模块绑定、token、时钟偏移 |

**实测（2026-11-13，见 `test-worksheets/runs/2026-11-13-firmware-size-budget.md`）**：

| 构建 | 体积 | 占 2 MiB 槽 |
|---|---|---|
| 基线（含立绘） | 1,538,864 B | 73% |
| +Wi-Fi | 2,106,013 B | **100.4%（超槽）** |
| +Wi-Fi+BLE | 2,696,665 B | **128%（超槽）** |
| **搬走立绘 +射频**（估算） | ≈1,750 KB | 85%，**余 ≈347 KB** |

**结论：立绘必须移入 `ffat`（或 TF 卡）才能引入射频；347 KB 是 Rust 内核的可用上限。**
**格式**：存**原始 RGB565**（135,200 B/张），零解码；RLE 留作后续。
**扩容优先级**：① 改分区表把 `app1` 扩到 4 MiB（`app0` 不变、恢复能力保留）→ ② 第二块 ESP32 做 BLE 协处理器（省 577 KB）→ ③ 更激进素材管理。**先做免费的"搬立绘"，② 留最后。**

### 5.5.4 更新策略（**有取舍，必须明确**）

| 方式 | 可行性 | 代价 |
|---|---|---|
| **USB 烧录到 `app1`** | ✅ 当前就用 | 每次要按 BOOT+RESET；**保住出厂 `app0` 恢复槽** |
| **OTA 双槽** | ⚠️ 需要两个**属于我们**的 app 槽 | 会**吃掉出厂 `app0`**（恢复能力换成"升级能力"）；或改分区表把 app 槽做大 |

**P0 建议：只走 USB 更新**，出厂恢复槽保留到产品化阶段再权衡。

### 5.5.5 看门狗、崩溃与日志

| 项 | 设计 |
|---|---|
| 任务看门狗 | 只挂 `ui_task`（最长 ≤2 s）；`sensor/reducer` 用自身超时保护，不吃全局 WDT |
| 崩溃 | panic → coredump 写 flash → 重启；开机读标记，进 `SystemOverlay` 显示"上次异常" |
| 日志 | 串口分级（error/warn/info/debug）；**生产默认 info**，debug 会拖慢 UI |
| 时间基 | 只用 `esp_timer_get_time()` 单调时钟；**不引入墙钟**参与融合（墙钟只给日志打标） |


## 6.5 下一阶段路线：M1–M5（2026-11-14 定）

**决策**：`AIM`（角速率高频流）**暂不启用**——`AngularRateSample` 从未实机验证（`GS-CONTRACT-005`），且射频共存未测。靶场可先用合成角速率跑通，等 IMU 验证后替换。

**顺序理由**：内核接进固件后，必须能通过帧协议"看见"它在做什么，所以**先协议、后台架、再板端、最后内核**。

| # | 里程碑 | 交付 | 验收 |
|---|---|---|---|
| **M1** | `STATE` / `EVENT` 载荷编解码 | protocol crate 新模块 | 往返 + 截断 + 越界 + 128 字节 ID 边界 |
| **M2** | PC 台架程序 | host 侧可执行程序 | 握手、收快照、收事件、发表情、断线重连、注入坏帧 |
| **M3** | 板端帧协议（与 ASCII 并存、可切换） | 固件 | 板 ↔ PC 实机收发一致 |
| **M4** | Rust 内核接进 `build.ps1` | 构建 + C ABI 调用点 | 板上串口可见 `revision` 随握持事件变化 |
| **M5** | Wi-Fi STA 自动发现 + 断线重连 | 固件 + 台架程序 | 拔插网络后状态不丢、不重放旧事件 |

**M4 的前置已完成**：`firmware/kernel-shim` 已用 xtensa-gcc 完成 C↔Rust 链接（`.text` 155.6 KB 上界）。

### 6.5.2 M3 上板验证步骤（工具已就绪，2026-11-14）

**前提**：一次物理按键（左 BOOT + 右 RESET）进下载模式。

1. 烧录新固件（含 `gs_wire.*`）。
2. 串口发 `WIRE on`，板子打印 `WIRE on boot_id=board-XXXXXX-1`。
3. 另开终端跑桥：`./scripts/serial-bridge.ps1 -Port COM3 -ListenPort 47900`
4. 再跑台架：`ailive-gun-spirit-bench --tcp 127.0.0.1:47900 15`
5. **通过判据**：`hello=1` 且 `states>=1`；板子每秒发一次 STATE。

**跨语言对照向量**（Rust 侧权威值，用于比对 C++ 编码是否一致）：

```
length = 97
hex = 01000003000E626F6172642D3030303030302D310100000000000000000000000000000000000100000000000000000001000000000000000000010000000000000000000100000000000000000001000000000000000000010000000000000000
```

构造条件：`boot_id="board-000000-1"`、`revision=1`、`produced_at=0`、六个 fact 全 `Unknown(NeverObserved)`、`node_health=[]`。
板端实际 `boot_id` 由 MAC 派生（同为 14 字符），因此**长度必然为 97**，只有中间 14 字节会不同——长度不符即为编码错位。

**注意**：`produced_at` 与 `revision` 会随时间变化，比对时应看**长度**与**字段偏移**，而不是整串相等。


**上板验证结果（2026-11-14，`MEASURED`）**

## 7. 待定与风险

1. **集成方式**：`no_std` 静态库链入 Arduino，还是纯 IDF-Rust 重写——由 CP1b 的体积/链接结果裁决（见 `HARDWARE_IMPLEMENTATION_PLAN.md` §0.1.3 的结构性提醒）。
2. **镜像余量**：当前 1,537,328 B / 2 MiB 槽；立绘占 ≈946 KB。若把立绘移入 `ffat`（11.875 MiB，空）可腾出 ≈1.44 MiB——但**先测加入内核后的实际体积**再决定。
3. **`AngularRateSample` 未验证**（`GS-CONTRACT-005`）：符号/轴向/量程都属设计值，首颗 IMU 后按协议变更抬版本。
4. **正式 OCLive 接入**：仍按所有者安排暂缓；先用 PC 台架测试程序。
