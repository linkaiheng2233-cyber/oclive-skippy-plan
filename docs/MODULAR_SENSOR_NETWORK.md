# 模块化无线感知网络（P0-A 配件形态）

**状态**：`CANDIDATE`（2026-11-13；所有者约束：**无走线 / 内部空间极少 / 组件做成配件 / 通用模块化按需组装**）
**唯一职责**：定义**模块分块、唤醒与延迟、电池策略、标准连接通道、操作界面、主机供电**六件事。
**不负责**：交互与表情（`FRONTEND_DESIGN_BRIEF.md` §9）· 传感器选型细节（`SENSOR_OPTIONS.md`）· 帧格式（`PROTOCOL_V1_DRAFT.md`）· 供电实测门（`MAIN_POWER.md`）

## 1. 为什么按"物理邻近"分块，而不是每个传感器一个模块

每增加一个无线模块 = 一块 MCU + 一块电池 + 一次充电维护 + 一次配对。**能用一根 20 mm 短线合并的，就不要拆成两个无线节点。**

| 模块 | 覆盖位置 | 板载件 | 位置 | 电池 |
|---|---|---|---|---|
| **主机（显示板）** | 导轨 | ESP32-S3 + 屏 + **IMU（必需）** | 导轨固定段 | 板载充放电 / USB |
| **M-A 握把组** | 后握 + 扳机（+可选保险） | FSR + 霍尔 | 握把底部小盒 | 纽扣（优先免充电） |
| **M-B 前部组** | 前握（+可选手电） | FSR + 触点 | 护木侧夹片 | 纽扣 |
| **M-C 枪托组** | 肩托抵肩 | FSR | 枪托后侧 | 纽扣 |
| **M-D 机匣组（可选）** | 拉栓/枪机释放 | 霍尔 | 机匣侧 | 纽扣 |

**首发覆盖全枪 = 主机 + M-A + M-B + M-C**（前/中/后三段全有）。M-D 后加。

**关键设计：扳机放进 M-A（握把组），不单独做无线模块。**
扳机护圈到握把底部只有 15–30 mm，同一小盒内一根短线即可 → **扳机走 GPIO 中断，不经过无线** → 彻底绕开"无线延迟"这个最大风险点。这是本方案唯一必须坚持的合并。

## 2. 模块怎么启动？延迟够不够？（核心问题）

### 2.1 不用"定时轮询唤醒"，用"事件唤醒 + 常连链路"

```
传感器电平变化 → GPIO 中断 → MCU 从 Sleep 唤醒(≈1 ms) → 立即组包 → BLE 发包
                                                       ↓
主机（显示板）收到 → 融合 → 表情即时反馈（不等待 PC）
```

- **MCU 不能被"关掉再连"**：BLE 断连后重连要几百 ms 到数秒，**那才是"立刻响应"的杀手**。
- 正确做法：**链路保持常连**（模块作为 BLE peripheral 持续连接），MCU 在 `System ON idle` 下睡，靠中断唤醒。唤醒后**直接写 TX FIFO**，不用重新建链。
- **连接间隔（Connection Interval）就是延迟下限**：模块只能在连接事件里发包，所以**要快就必须缩短间隔**——这是功率与延迟的唯一交换点。

### 2.2 数字（`ESTIMATED`，nRF52840 + 纽扣）

| 连接间隔 | 典型平均电流 | CR2032 220 mAh 估算寿命 | 事件延迟（唤醒→主机收到） | 适用 |
|---|---|---|---|---|
| 1000 ms | 15–25 µA | **≈1 年** | ~1 s | 肩托、慢变压力 |
| 500 ms | 25–40 µA | ≈6 个月 | ~0.5 s | 前握/后握（拿起动作） |
| 100 ms | 80–150 µA | **≈1–2 个月** | ~0.1 s | 更快握持反应 |
| 15 ms | 400–800 µA | **≈2 周** | ~0.02 s | 只给充电电池用 |

**结论：**
1. **扳机不需要无线**（已在 M-A 内解决）→ 最苛刻的 20 ms 级需求根本不用纽扣电池扛。
2. 握持/肩托是**人动作**，0.1–0.5 s 的识别延迟完全可接受（人手拿起/放下本来就是百 ms 级）。
3. **免充电（纽扣）优先 = 间隔 500 ms–1 s + 事件唤醒**，寿命 6 个月到一年，用户一年换一次电池，可接受。
4. **要"毫秒级"的模块（若将来做拉栓连发判定）改充电方案**——由用户在购买时选：**免充电版（纽扣，慢一点）/ 充电版（小 LiPo，快一点）**。同一块 PCB，两种电池仓。

### 2.3 另一个延迟来源：主机侧

- 主机（显示板）融合 + 渲染：表情最短驻留 300 ms（交互方案 §9.5），所以**感知端 100–500 ms 与显示端的 300 ms 同量级**，不构成瓶颈。
- **不要**让模块的观测绕去 PC 再回来：板端本地融合、本地出图（ADR-069）。

## 3. 电池策略：一块板，两种供电仓

| 版本 | 电芯 | 充电 | 适用 | 备注 |
|---|---|---|---|---|
| **免充电版（优先做）** | CR2032 / CR1632 纽扣 | **不需要** | M-A/M-B/M-C 首发 | 符合既有规则：纽扣电池只用于**专用低功耗节点**，且绝不接充电路径 |
| 充电版 | 100–300 mAh 小 LiPo | USB-C + TP4056 类 | 需要更快响应的模块 | 多一个充电口与维护动作 |

**PCB 设计要点**：纽扣仓与 LiPo 仓做成**两种可选贴装/插接座**，同一块板两种装法；固件读电池电压即可知道是哪一种（阈值不同）。

## 4. 标准连接通道（产品化关键）

目标：**拿到模块 → 装上 → 主机点一次"添加" → 就能用**。

```
模块上电
  → BLE 广播：module_uid + profile_id(支架编码) + capability 位图 + 电量档
主机（显示板）进入「配对新模块」界面
  → 选中模块 → 建立连接
  → 读 NodeHello（版本/能力/位置标识）
  → 绑定：写到 NVS（module_uid → 位置 + 能力）
  → 之后自动重连（白名单，不再广播）
```

| 要素 | 设计 |
|---|---|
| **身份** | `module_uid` = MCU 唯一 ID（nRF52 有 64 位 FICR DEVICEID）；用户不可改 |
| **位置** | 由**支架编码**决定（支架上一颗固定电阻/磁编码），模块读支架即知自己是"肩托"还是"前握" |
| **能力** | 由固件声明 + 位置决定（例如同是霍尔，装在扳机护圈=主控触点，装在弹匣井=弹匣在位） |
| **配对方式** | 主机 UI 列表选择（不做物理配对键，省一个件）；同一时间只允许 1 个模块处于配对广播 |
| **断线策略** | 自动重连；连续失败 30 s → UI 显示"模块离线"，但**不影响其它模块与主闭环** |
| **安全** | 首版不做加密（自有 BLE 连接 + 白名单 MAC）；产品化前再评估 |

**与契约的关系**：这套"自报能力"就是 `NodeHello`（`GS-CONTRACT-004`）——**无线模块化让 `NodeHello` 从"可延后"变成 P0 必需**。

## 5. 操作界面（硬件层 UI，MVP）

在主机 480×320 屏上，把"角色主界面"之外的功能收进设置页（长按或三击进入）：

| 页面 | 内容 | MVP 取舍 |
|---|---|---|
| **模块管理** | 已绑定模块列表：位置/电量/最后上报/延迟 p95；添加、重绑、解绑 | ✅ 必做 |
| **能力开关** | 每个联动点启用/禁用（例如"肩托→专注表情"关掉） | ✅ 必做 |
| **校准** | IMU 两点校准、肩托/前后握阈值零点 | ✅ 必做 |
| **模式** | 自由 / 靶场 / 离线预设 | ✅ 必做 |
| **诊断** | 丢包率、重连次数、错误计数、版本 | ✅ 只读页 |
| 外观/主题、角色包管理 | — | ❌ 后置 |

**原则**：三个层（`FRONTEND_DESIGN_BRIEF.md` §9.1）不变，设置页作为 `SystemOverlay` 的扩展；**任何设置操作都不能打断即时表情反馈**。

## 6. 主机供电：先成品、后开源

| 阶段 | 做法 | 说明 |
|---|---|---|
| **P1（现在）** | 先买成品：**TP4056 充电板 + 1S 保护板 + MT3608 升压（或 IP5306 模块）** | 目标是验证"充放电 + 5 V 输出 + 边充边用行为"，不动 PCB |
| **P2（产品化）** | 出一块**开源电源小板**（KiCad 原理图 + BOM + 测试点）：1S LiPo + power-path（如 BQ24074 / IP5306 类）+ 5 V 升压 + 电量计（如 MAX17048）+ 电池开关 | 需要实测电流/温升后再定拓扑；**开源**指资料齐全可复现 |

**与板载 U2 的关系**：晶彩板上已有 U2（疑 IP5306H，未锁料号）。开源小板是**并行路线**：若 U2 确认可用则直接用；若充电电流不合适（可能固定 ~2 A），开源小板就是替代方案——这正好回答"主机供电做成充放电"的诉求。

## 7. 模块固件：建议 Rust + 复用同一份契约类型

- CP1 已证明 `contracts`/`perception-core` 能在 `no_std + alloc` 下编译。
- nRF52840 目标 `thumbv7em-none-eabihf` 同样可跑 `no_std` → **模块固件可以直接用同一份 Rust 契约类型**，不必另写一套 C 结构体。
- 候选框架：**embassy**（async、生态成熟）或 nRF SDK（C）。
- 收益：`SensorObservation`/`AngularRateSample` 的类型与校验**全链路一份**，跨语言 golden vectors 的负担大幅下降。
