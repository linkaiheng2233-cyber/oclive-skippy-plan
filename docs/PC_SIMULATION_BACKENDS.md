# 主机侧娱乐后端：屏幕打靶与投影靶场（设计基线）

**状态**：CANDIDATE（2026-09-23；项目所有者提出「结合电脑做空枪打靶、投影靶场、参考游戏做靶场交互与 wargame 特色」的方向，尚未裁决）  
**修订（2026-09-23 晚）**：瞄准通道改为**「陀螺速率控制」首选、相机降为按需**——依据所有者提出的「类似手柄陀螺仪校准后在电脑上模拟，甚至可以省掉摄像头」。见 §3、§4。  
**唯一职责**：定义「以 PC 为主机时的**娱乐性打靶 / 靶场 / 投影模拟**」这一方向的目标、架构定位、瞄准通道选型、延迟归属、枪侧改动量、玩法范围、安全与文案红线、分阶段路线与待决项。  
**不负责**：感知契约字段（以 `ailive-gun-spirit-contracts` 为准）、角色表达与人格（OCLive 兄弟仓）、投影仪/相机采购细节（采购核对清单）。  
**上游**：`DECISIONS.md` 的 ADR-063 / ADR-066 · `ESP32_GUN_ASSISTANT.md` · `PROJECT_BOUNDARIES.md` · `PROJECT_BASELINE.md`  
**下游**：`ROADMAP.md`（**须独立立项，不进入器灵核心**）· `test-worksheets/采购核对清单.md` · `PROJECT_BOUNDARIES.md` §4（**仅在 ADR-066 升为 ACCEPTED 后才新增行**）

## 1. 一句话目标

**枪不再只是「被聊天的对象」，而是屏幕上娱乐内容的输入设备**：空枪对着 PC 显示器或投影幕打靶，枪娘从「陪聊」变成「陪你打靶的搭档」。全部游戏逻辑与算力在 PC；**枪侧硬件零改动**，只多一个「模式位」。

## 2. 架构定位：这是**新的输出消费者**，不是新感知

```
传感器 → PerceptionState → DeviceEvent ─┬─→ OCLive（角色表达）
                                        └─→ 娱乐后端（打靶/靶场/计分）  ← 新增
                                                     ↓
                                              Output Arbiter
```

三条纪律：

1. **游戏后端与 OCLive 并列，互不写入。** 游戏数值不直接变成角色台词（避免「报分机器人」）；角色表达仍只由 OCLive 出。
2. **命中和得分属「游戏事实」，必须有独立 provenance，不得冒充感知事实。** `PROJECT_BOUNDARIES.md` §6 已写死：FSR / IMU / 辅助触点**不证明击发、命中、伤势、目标或危险距离**。游戏层的「命中」是画面几何判定结果，与感知内核无关。
3. **`control.primary.engaged` 只证明「触点状态」。** 游戏把它当作**开火输入**是游戏语义，不是物理声明；内核与契约文档中不得改称「击发」。

## 3. 瞄准通道：三案对比（核心选型）

| 方案 | 原理 | 上下（俯仰） | 左右（偏航） | 额外硬件 | 遮挡 / 场地 | 门槛 |
|---|---|---|---|---|---|---|
| **A′　陀螺速率控制（首选）** | **像手柄陀螺瞄准**：准星按角速率移动（**相对控制**，靠玩家眼睛闭环），**不做绝对屏面映射** | 走速率（重力可给出绝对俯仰） | 走速率，**有漂移、需回中** | **0 元**（IMU 已有） | **无遮挡、任意场地、不受光照影响** | 新契约版本（角速率观测 + 能力协商） |
| **B　主机摄像头 + 枪上标记** | PC 摄像头识别枪上刚性标记阵列 → PnP → 屏幕坐标（**绝对**） | 好 | 好（标记阵列 15–20 cm、2 m、1080p ≈ 落点 2–5 cm，`ESTIMATED`） | 0–40 元 | 需标记可见、相机视场覆盖、光照稳定 | 相机通道（**触及边界门 5**） |
| **C　不瞄屏幕的节奏玩法** | 只做「扣扳机时机 + 换弹速度」的反应 / 节奏玩法 | — | — | 0 元 | 无限制 | 低 |

**A′ 为什么是首选**：它**不需要知道站位距离、不需要屏幕位姿、不需要标记与标定**——速率控制没有「绝对几何」这一环，因此也没有「标定失败」这一环；玩家的眼睛就是闭环。这正是主机手柄陀螺瞄准成立的原因。

**A′ 的诚实代价**：精度与手感是「手柄陀螺」级，不是「打靶比环数」级。打气球、罐子、飞盘够用；要打小靶或比环数，才需要 B。漂移与回中见 §3.2——**那是结构，不是选项**。

**阶梯（成本递增，每步可独立交付价值）**：**C（0 元，先验证「扣扳机 → 画面反馈」）→ A′（0 元，陀螺瞄准）→ B（想要绝对参考 / 小靶精度时再上相机）**。

### 3.1 允许与禁止的分界线（**一句话规则**）

> **「瞄准射线 × 屏幕平面」求交是允许的；任何引入弹道、初速、飞行时间、下坠、风偏、命中概率或自动修正的计算都是禁止的。**

- 界面上称**准星 / 光点**，**不称「弹着点」**；
- **禁止任何形式的辅助瞄准、吸附、命中修正、后坐补偿**——可以**测量**玩家瞄向哪里，**不可以修正**它；
- 游戏层只做「射线与靶面是否相交」的判定，不做投射物动力学；
- 相机方案下同一规则收紧为：**只允许修正传感器漂移，不允许修正玩家意图**（见 §3.2 第 8 条）。

### 3.2 校准与漂移控制（A′ 的工程要点）

1. **零偏自动校准（静止即校准）**：检测角速率与加速度方差均低于阈值并持续 0.3–0.5 s → 用滑动平均更新零偏。开机时提示「把枪平放 2 秒」。
2. **漂移是必需处理项**：残差 **0.5 °/s → 60 s 累积约 30°**；**0.1 °/s → 60 s 累积约 6°**（都能毁掉瞄准）。因此以下三条是**结构**：① **放下枪（`pose.lowered`）自动回中**；② **准星边缘夹持**（到屏幕边缘后丢弃同向漂移）；③ **静止 ZUPT** 持续修正零偏。
3. **IMU 预热**：MEMS 陀螺需约 30–60 s 达热平衡，预热期零偏漂移明显更大（`ESTIMATED`，**需实测**）→ 枪侧屏显示「陀螺仪热身中」；既是工程需要，也天然是开机仪式。
4. **接口选择**：优先 **SPI IMU（QMI8658 / ICM-42688 类）** 并以 **DRDY 中断 / FIFO 驱动采样**，而不是主循环轮询 I2C——**采样节拍稳定性直接决定准星平滑度**。MPU6050（I2C）可起步，节拍与温漂更差。
5. **职责划分**：**固件**负责采样、滤波、去零偏、**定频发送（建议 100 Hz）+ 时间戳**；**主机**负责积分、灵敏度、平滑、回中、夹持与渲染。主机有时钟与算力，滤波参数改动不必刷固件。
6. **灵敏度不做强制标定**：速率控制不依赖站位几何，给一个「灵敏度」滑杆 + 试射即可（与手柄一致）；可选做一次「从屏幕左缘扫到右缘」的自动标定。
7. **平滑 vs 延迟的权衡**：低通滤波抑制手腕抖动但增加延迟；默认偏平滑，参数开放给玩家。
8. **相机将来若用于重定位**：只允许修正**传感器漂移**（例如周期性重锚定零偏），**不允许**把准星拉向目标——后者仍是 §3.1 的禁止项。

## 4. 延迟归属（**两条瞄准路径完全不同**）

| 路径 | 闭环在哪 | 链路承载什么 | 关键指标 |
|---|---|---|---|
| **A′ 陀螺速率** | **枪 → PC 链路**（约 100 Hz 瞄准流） | **高频率角速率** + 离散事件 | **链路 p95 与抖动**（不是平均值） |
| **B 相机标记** | **主机视觉内闭合** | 只有离散事件（扣扳机 / 换弹 / 举枪） | 相机帧率与光照 |

- **A′ 在 USB-CDC 上毫无压力**：100 Hz × 约 12 B ≈ **1.2 KB/s**，延迟毫秒级 → **有线是 A′ 的默认前提**。
- A′ 走 **Wi-Fi 2.4G** 时带宽同样无压力，但 **p95 与抖动仍是 `UNKNOWN`**，必须实测；抖动过大时主机只能靠外推 / 平滑补偿，**手感会变钝**。
- 两条路径下，ADR-063 的「事件到画面 p95 ≤ 100 ms」门都**不约束准星本身**（A′ 需要的是抖动指标，B 需要的是相机帧率）；该门继续约束**角色反馈**与**离散事件**。
- 枪侧屏的角色反馈继续容忍 100 ms，**且不参与命中判定**。

**推论（两处都成立）**：**游戏模式恰好是有线场景**——USB-CDC 的毫秒级延迟同时满足扣扳机与陀螺瞄准流；D1 选择 USB 在游戏玩法上第三次被证明是对的。

## 5. 枪侧零改动 + 模式位扩展

- 模式从双态扩为**三态**：**自由聊天 / 靶场游戏 / 离线预设**（扩展 `ESP32_GUN_ASSISTANT.md` §3）。
- 下行仍是 `AssetRef` + 短文本 + 状态位 + 模式；靶场模式新增的「得分 / 弹药 / 命中提示」只是**状态位扩展**，不引入新下行类型（若引入，须走能力协商）。
- 枪侧屏在靶场模式只显示**枪娘表情 + 极简状态位**，**不作为游戏主画面**——主画面在 PC/投影，避免小屏抢戏，也避免把 4.6 MB/s 的像素流塞进无线链路。

## 7. 安全与文案红线（**必须在 ADR 中写死**）

**安全仪式（同时是角色设定）**：进入靶场模式前，枪侧屏与 PC 依次确认 **① 空仓（无弹匣、无弹）② 前方无人 ③ 不在有实弹的场所**。把确认做成**角色的仪式化行为**（「先让我检查一下」），既满足安全要求，又自然融入体验。

- 载体仅限**玩具 / 模型载体**（RADIAN MODEL 1 水弹或软气枪级），**不得与真枪配合**；
- 只在封闭空间使用；不得指向窗户、门、走道方向；
- **禁止清单**：弹道 / 初速 / 风偏 / 下坠 / 命中概率 / 射击解算；任何形式的辅助瞄准、吸附、命中修正；目标检测、目标跟踪、人体识别；把成绩用于训练或军警用途；产品文案出现「射击训练 / 战术训练 / 军警」字样。
- **对外定位**：**娱乐性打靶游戏**（与消费级光枪游戏同类），**不使用「训练」作为产品定位**。
- **相机隐私边界**：画面**只用于几何解算**，不存储、不上传、不送模型、不进角色记忆；只把「屏幕坐标 / 命中结果」这类语义量交给游戏层与 OCLive。此条与「原始采样只在节点/驱动层处理」同一逻辑。

## 8. 分阶段路线

| 阶段 | 内容 | 依赖 | 成本 |
|---|---|---|---|
| **G0** | 屏幕打靶最小闭环：扣扳机 → PC 画面反馈（方案 C，无相机、无瞄准） | 扳机触点（外部只读）+ USB-CDC | 0–20 元 |
| **G1** | **陀螺速率瞄准**（方案 A′：无相机、无标记、无额外硬件） | 固件角速率流 + 新契约版本（能力协商）+ §3.2 的校准与回中 | **0 元** |
| **G2** | 计分 / 连击 / 关卡 + 换弹玩法 + 枪娘解说 | G1 | 0 元 |
| **G3** | **（按需）** 相机标记：绝对参考、小靶精度、免回中 | 触及边界门 5，届时单独走评审 | 0–40 元 |
| **G4** | 投影靶场（大画面） | 投影仪 | 300–3000 元（可后置或借用） |

**G0 是性价比最高的一步**：它不需要相机、也不需要瞄准通道，就能回答「枪当游戏输入设备好不好玩」这个最关键的问题。**G1 是第二个 0 元跳跃**：瞄准能力完全来自已有的 IMU，只差一个契约版本与固件里的一条速率流。

## 9. 待决项

1. **扳机检测的机械方案（阻塞 G0）**：① 护圈外侧微动开关由扳机刃推动；② 护圈外侧霍尔 + 扳机贴小磁铁（非接触）；③ **完全不碰枪**——握把上加按键（街机式「开火键」）。三者都**不进入发射器内部、不连接原火控/电机/供弹**，因此不触发 `PROJECT_BOUNDARIES.md` §7 门 2；但它是**新增用途**（游戏开火判定），仍须 ADR 明确「外部、只读、非侵入」。方案 ③ 零机械风险但真实感最差。

   **一条已评估并被否决的路径（2026-09-23）**：所有者提出「**通过火控来实现**」扳机检测（读取或接入原发射器的火控 / 扳机开关电路）。**未采纳**，理由如下：

   | # | 理由 |
   |---|---|
   | 1 | `AGENTS.md` 红线明确：**P0 不接 RADIAN 内部火控、扳机或供弹机构** |
   | 2 | 触发 `PROJECT_BOUNDARIES.md` §7 **门 2**（新线路进入发射器内部或连接原火控/电机/供弹），必须先 ADR 评审 |
   | 3 | 即使过门，也必须同时满足四条：**只读、不并接驱动回路（光电隔离）、故障不得影响供弹与发射、可逆可维护** |
   | 4 | 更根本的是**可移植性与定位**：接原枪电路会让「通用电子核心 + 可更换底座」退化为**绑定单一载体**，并把娱乐配件变成「改动过的发射器电子」，责任面与保修面同时扩大 |

   **等效替代**：外部只读耦合（①②③）拿到的是**同一个事实**——扳机**机械位置**，而这正是 v0.2 契约 `AuxControlContact(primary_trigger)` **已经预留的语义**（「辅助触点只证明触点状态」），**连契约都不用改**。反之，火控信号是**另一种语义**（可能含单发/连发/电子开关逻辑与延时），接入后反而要新增契约解释，并让感知内核开始"理解火控"。
2. **契约 v0.3 的范围（阻塞 G1）**：v0.2 的 `SensorObservationKind` 是**闭集枚举 + `deny_unknown_fields`**，**任何新观测种类都无法"悄悄加"**——角速率必须靠新契约版本。建议把**① 能力协商（hello + 能力集）、② 角速率观测、③ 只读换弹（弹匣在位/拔出）合并为一次 v0.3 升级**，能力协商做载体，后两者是首批能力；避免三次版本跳跃。这也正是 `ESP32_GUN_ASSISTANT.md` §9.3 第 4 项要补的主体。
3. **IMU 选型与实测（阻塞 G1 的手感）**：优先 **SPI + DRDY 中断**（QMI8658 / ICM-42688 类），MPU6050（I2C）可起步；**建议各买一个由实测裁决**（15–35 元）。实测项：静止噪声、零偏重复性、温漂、预热时间、100 Hz 节拍抖动——**建议并入 ADR-063 的台架实验清单**（与 FSR ADC、Wi-Fi 丢包一起做）。器件对比表与「IMU 是什么」见 `ESP32_GUN_ASSISTANT.md` §9.3 第 5 项。
4. **相机（G3，按需）**：不再是前置。若将来启用，才需要裁决它与 P1「娱乐观察」是**同一条通道还是两条**，以及 capability 命名。
5. **是否投影立项**：成本 + 场地（需暗环境、平整幕面）决定 G4 时机。
6. **娱乐后端的落地形态**：建议**先作为 `ailive-gun-spirit-host` 内的独立模块**（不进感知内核、不依赖 OCLive 内部对象），**不急于新增第 4 个 crate**——workspace 成员数有门禁断言（`GS-BOUNDARY-001`），新增 crate 必须同时显式更新该门禁与依赖 allowlist。
7. **若本方向被接受**（升格动作）：ADR-066 由 `CANDIDATE` 升为 `ACCEPTED`；`PROJECT_BOUNDARIES.md` §4 新增「游戏/模拟」行并更新「最后核对」；`ROADMAP.md` 按「**必须独立立项、不进入器灵核心**」加条目；`采购核对清单.md` 增相机（可选）/ 投影对应行；同步 `ESP32_GUN_ASSISTANT.md` §3 的三态模式。
