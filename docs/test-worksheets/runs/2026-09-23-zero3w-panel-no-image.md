## 1. 现象

链路参数全部正常，但屏幕只有**一条竖线**（背光会随模式变化亮起）：

| 已确认正常 | 值 |
|---|---|
| HPD | `connected` 稳定 |
| EDID | 驱动内部解析成功：`edid parse block0/block1 finish`、`drm get edid support modes: 5` |
| 模式选择 | `drm hdmi mode set: 480*800`、`hdmi drv has been enable!`、`drm hdmi atomic enable` |
| CRTC / 平面 | `crtc[99] mode: "480x800": 60 34860 480 500 510 700 800 801 803 830`；`plane[92] crtc=DE-0 fb=163` |
| 帧缓冲 | `/dev/fb0`，virtual `480,1600`，fbcon 已绑定 |

**面板行为**：背光随模式切换亮起（说明收到了信号并尝试锁定），但画面只有一条竖线。

## 2. 关键交叉证据（改变结论方向）

**同一块小屏在 PC 上能正常显示桌面**（项目所有者实测，使用另一根标准 HDMI 线）。  
⇒ 面板、面板 EDID、面板所需时序**本身可用**；问题出在"板子 → 面板"这一侧。

## 3. 被证伪或被排除的假设

| 假设 | 结论 | 依据 |
|---|---|---|
| 线缆 DDC 故障 | 已排除 | 换绿联线后 EDID/HPD 全部正常（见上一份运行记录） |
| 分辨率/模式未设置 | 已排除 | CRTC 与平面均在按面板 EDID 的原生时序扫描输出 |
| `video=` 参数未生效导致模式错 | **确认为真但非根因** | 驱动忽略 `video=`，优先用 EDID 首选模式；即使用 EDID 原生模式仍无画面 |
| 面板 EDID 是错的（克隆 EDID） | 部分成立 | 面板名为 `HDMI480x800HH`，DTD 图像尺寸字段是垃圾（480×800 **mm**）、DTS 解析报 `pixel clock[0KHz] invalid`；但面板在 PC 上可用，说明其实际所需时序可被 PC 满足 |
| 用 EDID 覆盖强制微雪官方时序可解决 | **无效（功能不存在）** | 本内核 `drm_kms_helper` **没有 `edid_firmware` 参数**（只有 `drm_fbdev_overalloc`/`fbdev_emulation`/`poll`），EDID 覆盖未编入内核；自制的 `edid/hdmi480x800-waveshare.bin` 未被加载 |

## 4. 本轮吃到的两个驱动限制（重要，勿重复踩）

1. **不能用 `modetest` 改模式**：对连接器执行 `modetest -s 146@99:<mode>` 会让 **SSH 会话断开并使板子崩溃重启**（实测两次，一次直接重启）。厂商驱动的 atomic commit 路径不安全。→ 想换模式只能改内核命令行并在**开机时**生效。
2. **不能靠 `video=` 覆盖 EDID 首选模式**：驱动在 1.16s 按 EDID preferred 选定 `480*800`，命令行里的 `video=HDMI-A-1:800x480@60` 只作为额外模式（`type: userdef`）存在，不会被优先选中。

## 5. 当前最可能的根因（待验证）

驱动日志有一行值得注意：

```
sunxi hdmi select vic 0 use hdmi14 vsif
```

`VIC 0` 表示该模式**不在 CEA 标准模式表内**（480×800 本就是非 CEA 模式），驱动改用 **HDMI 1.4 vendor-specific infoframe** 发送。廉价屏的 HDMI 接收芯片常在这种"非标准模式 + 厂商信息帧"组合下无法正常同步；而 PC 显卡对同一模式的处理路径不同，因此 PC 能显示、板子不能。

其他同向可能：板子 HDMI 输出对这块屏的**信号裕量偏紧**（TMDS 幅度/预加重），加一级中继通常可解。

## 5.1 面板 EDID 完整解码（2026-09-23 晚，从 PC 注册表恢复 256 字节）

> **型号前提更正（2026-09-23 晚，所有者澄清）**：本件是 **3.2 英寸** 480×800 IPS LCD 模块（卖家标题为"3.2寸 IPS 屏幕 LCD 液晶屏"类通用名），**不是**此前记录的"微雪 3.5 英寸 480×800"。本文与其它文档中凡以微雪 3.5 英寸模块规格（含 88.87×52.56×7.15 mm、300 cd/m²、触摸款）作参照之处，**只作候选屏规格参考，不代表本件**；本件的模组外廓、驱动板与主控芯片型号均待测（`GS-HW-004`）。克隆 EDID 的判断不受影响：驱动板固件里的 EDID 就是一份拼装件。

- 恢复路径：`HKLM\SYSTEM\CurrentControlSet\Enum\DISPLAY\LEN1086\<instance>\Device Parameters\EDID`（256 字节）
- 解码工具：`E:\OCLive\oclive-四季宝-artifacts\bringup-toolchain\decode-edid.ps1`（自写，ASCII-only，注意 PowerShell 的 `-shl` 对 `[byte]` 会按字节回卷，必须显式 `[int]` 转换）
- 同一性核对：**与 2026-09-23 板端读到的前 32 字节逐字节一致** → 同一块屏，且 PC 缓存件是完整可信副本
- 两段校验和（基块 `0x58`、扩展块 `0xD9`）**均合法**（各自 128 字节和 mod 256 = 0）→ 异常是固件"就这么写的"，不是传输或读取损坏

| 字段 | 值 | 判读 |
|---|---|---|
| 厂商 ID / 产品码 | **`LEN`（Lenovo）/ `0x1086`** | 驱动板固件里装的是联想显示器的 EDID，而不是本件面板的；480×800 正是 2011 年前后联想手机/平板面板的常见分辨率，符合"模板抄自同分辨率旧面板"的推断 |
| 生产周/年 | **2011 年第 34 周** | EDID 1.3 时代的模板 |
| EDID 版本 / 输入 | 1.3；数字输入，位深与接口类型**均未定义** | 老式做法，不是现代 HDMI 屏的写法 |
| 首选 DTD | `480x800`，**34.86 MHz**，HTOTAL 700 / VTOTAL 830，Hfp/Hsw=20/10，Vfp/Vsw=1/2，`H-sync- V-sync+` | 与板端实际输出的时序**完全一致**（板端 CRTC：`60 34860 … 700 … 830`）→ 时序不是差异点 |

| YCbCr | 4:2:2 = 支持；4:4:4 = 不支持 | — |

### 这批数据能定什么、不能定什么

**能定**：

1. 这块屏的 EDID **是手工拼装的克隆件**（联想厂商码 + 通用名称 + 2011 年 + 自相矛盾的范围限制 + 空的 DTD 区 + VIC 0），不是一份自洽的标准 EDID。
2. 它**声明自己有 CEA 扩展与 HDMI VSDB**，却**没有声明任何标准 CEA 模式**（唯一 SVD 是 VIC 0）→ 这正是"源端一旦走非 CEA 路径（`VIC 0` + `hdmi14 vsif`）就无参考模式可依"的典型组合。
3. 板端驱动日志里那 5 条 `pixel clock[0KHz] invalid` 得到解释：解析器按 CEA 扩展的 DTD 区扫到 5 个槽位，槽位里是垃圾而非 DTD。

**不能定**：

- EDID 里**没有任何字段**能回答"这块屏接不接受 DVI 信令（无信息帧）"。HDMI 规范要求接收端兼容 DVI 输入，因此 `D` 标志实验（见 §6 ⓪）仍然值得一试，但它既不被这份数据支持、也不被否定。
- 也无法回答接收端芯片能否锁住 480×800（PC 上能显示说明可以，但需确认 PC 当时实际输出的分辨率）。
- **能真正回答这两问的是面板驱动板上的主控/桥接芯片型号**（丝印）：拿到型号即可查其数据手册，确认它是否要求标准 CEA 时序、是否支持 DVI 模式。这是买屏前/换屏前值得记录的一条硬数据。

## 6. 下一步（按性价比）

| 方案 | 成本 | 能判定什么 |
|---|---|---|
| **⓪ 命令行强制 DVI 信令**：`video=HDMI-A-1:480x800@60D`（`D` 由通用 DRM 解析为 `DRM_FORCE_ON_DIGITAL`，跳过 AVI/VSIF 信息帧） | 免费 / 2 分钟 | 把根因在"信息帧不兼容"与"TMDS 信号裕量"之间**二选一**（板端像素时序与 PC 完全一致，差异只剩这两处）。**判读前提**：该厂商驱动是否采用此标志未验证——必须比对 dmesg 的 `select vic 0 use hdmi14 vsif` 行有无变化；不变则本次**无效**。**提案·未实测**（2026-09-23 Claude 提出，见交接 §2.6） |
