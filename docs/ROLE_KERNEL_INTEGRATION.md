# 三块分离：感知内核 / 游戏 / 角色内核

**状态**：`CANDIDATE`（2026-11-14，所有者提出方向）。**本文只定边界与契约，不含实现。**
**一句话**：**感知归感知、游戏归游戏、扮演归扮演**；角色内核同时接收前两者的**带来源标签**的数据，产出角色表达，分发给游戏与屏幕。

---

## 0. 为什么拆成三块

当前闭环是「感知 → 表情」，角色只是被动反应。所有者要求让角色**参与游戏**，这带来一个结构风险：如果游戏直接把命中、比分塞给屏幕，或角色内核直接读游戏内部状态，三件事会纠缠成一团，之后**无法单独替换任何一块**（换游戏要改角色、换角色要改游戏）。

拆成三块后，每一块都能独立替换、独立测试、独立失败。

---

## 1. 三块边界

| 块 | 跑在哪 | 输入 | 输出 | 不做什么 |
|---|---|---|---|---|
| **A 感知内核** | ESP32-S3 板 | 传感器原始信号 | `PerceptionState`（1 Hz）、`DeviceEvent`（边沿），契约 v0.4 | 不读游戏数据、不决定角色说什么 |
| **B 游戏** | PC | 玩家输入、场景文件 | **`GameSignal` 流**（游戏事实，独立版本号） | 不改设备状态、不直接驱动屏幕表情 |
| **C 角色内核** | PC（OCLive） | ①`PerceptionState/DeviceEvent` ②`GameSignal` ③用户输入 ④角色包 | **`RoleCue`**：表情 id、台词、语音 cue、优先级、TTL | 不计算命中、不碰瞄准、不写感知事实 |

**方向固定**：A → C、B → C、C → 屏幕与游戏（**表现层**）。**任何一块都不得绕过 C 直接驱动角色表达**（系统状态提示除外，见 §5）。

---

## 2. 数据流

```
   ┌────────────┐   PerceptionState / DeviceEvent (v0.4)
   │ A 感知内核  │ ───────────────────────────────┐
   └────────────┘                                │
                                                 ▼
   ┌────────────┐   GameSignal (game v0)   ┌─────────────┐   RoleCue   ┌──────────┐
   │ B 游戏      │ ───────────────────────▶ │ C 角色内核   │ ──────────▶ │ 屏幕 EXPR │
   └────────────┘                          │  (OCLive)   │             └──────────┘
        ▲                                   └─────────────┘
        │           表现层（表情/语音/台词，**不影响命中判定**）
        └───────────────────────────────────────────┘
```

**关键约束**：C → B 的输出**只能影响表现**（角色说什么、什么表情），**不得进入 B 的命中判定与计分**。否则等价于辅助瞄准。

---

## 3. 契约：`GameSignal`（游戏块 → 角色内核）

**独立于设备契约**，放在新 crate（建议 `ailive-gun-spirit-role-bridge`），**不进** `contracts`——设备契约是闭集，不该被游戏概念污染。

| 字段 | 说明 |
|---|---|
| `game_session_id` | 一局游戏的标识（与设备的 `producer_boot_id` 无关） |
| `sequence` | 局内递增，用于去重与排序 |
| `emitted_at_ms` | 游戏侧单调时间（只在本局内比较） |
| `provenance` | **固定 `Game`**——与感知事实严格区分 |
| `kind` | 见下 |

**信号种类（MVP，刻意少）**：

| kind | 何时发 | 用途（角色） |
|---|---|---|
| `round.started` | 开局 | 进入状态、说开场 |
| `round.ended` | 结算 | 评价表现 |
| `hit.confirmed` | 命中 | 欢呼/短反应 |
| `miss.recorded` | 未命中 | 安慰/吐槽 |
| `target.destroyed` | 目标消失 | 短反应 |
| `streak.reached` | 连击达成 | 高强度表达 |

**红线**：`GameSignal` **不得**转化成 `SensorObservation` 或 `DeviceEvent`；它只进角色内核。

**粒度取舍（待定）**：每次射击都发 vs 只发聚合（见 §7 Q1）。

---

## 4. 契约：`RoleCue`（角色内核 → 屏幕/游戏）

| 字段 | 说明 |
|---|---|
| `cue_id` | 去重与回执 |
| `expression_id` | **必须属于固件 7 个表情 id**，否则设备丢弃并回 NACK |
| `speech_text` | 可选，PC 侧播放/显示（P0 板端无音频） |
| `voice_cue` | 可选，离线语音包 id |
| `priority` | 1–5，与设备预设同口径 |
| `ttl_ms` | 过期即失效，避免旧反应盖住新状态 |
| `source` | `Role` / `System`（系统提示优先级见 §5） |

**发送**：复用现有帧协议 `EXPR`（已是设备支持的下行），**不改协议**。

---

## 5. 仲裁与延迟分层

| 层 | 谁 | 预算 | 失败表现 |
|---|---|---|---|
| **即时层** | 板端内核 + 发行版反应表（已有） | ≤300 ms | 无，照常显示 |
| **角色层** | C 角色内核（可能含 LLM） | 秒级，异步 | **不得阻塞即时层**，超时即丢弃 |

**仲裁规则**：
1. 系统状态（离线/错误/升级）优先于角色情绪；
2. 角色层未及时返回 → 保持即时层表情；
3. 同一 `expression` 在最短驻留期内不重复触发（已有机制）。

---

## 6. 三块的独立失败模式

| 故障 | 期望行为 |
|---|---|
| B 游戏崩溃 | C 仍按感知驱动表情；屏幕提示"游戏未运行" |
| C 角色内核崩溃 | B 照常计分；A 的即时表情继续（发行版反应表兜底） |
| A 感知离线 | C 收到 `Unknown` 事实，可用游戏数据继续（但不得编造感知事实） |
| 网络断开 | 三段各自本地降级，不连锁 |

## 7. 待所有者裁决

1. **`GameSignal` 粒度**：每次射击都发，还是只发聚合（每局/每 5 秒）？前者表达丰富、后者省资源。
2. **角色内核后端**：先用本地确定性实现（规则/模板）跑通三段流，还是直接接 OCLive 真实适配器（当前 `PAUSED_BY_OWNER`）？
3. **游戏表现层范围**：C → B 只允许表情/台词，还是也允许角色影响场景（例如角色"加油"时背景变色）？
4. **`RoleCue` 是否进帧协议新增类型**，还是继续复用 `EXPR`（本文建议复用，零协议改动）？

## 8. 落地顺序（每阶段独立可验收）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S1** | `GameSignal` 类型 + 生成器（模拟一局）+ 校验/测试 | 能产生一局完整信号流并被解析 |
| **S2** | `RoleCue` 类型 + **本地确定性后端**（规则/模板） | 输入感知+游戏 → 输出表情与台词 |
| **S3** | 角色内核 → 设备：`EXPR` 下发，真板子显示 | 板端表情随游戏事件变化 |
| **S4** | 接入 OCLive 真实适配器（替换本地后端） | 同一 `RoleCue` 接口，后端可换 |
| **S5** | 语音/聊天室（PC 侧） | 离线语音包播放、聊天面板 |
