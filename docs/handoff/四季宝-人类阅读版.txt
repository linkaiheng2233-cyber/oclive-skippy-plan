A.I.Live-ai枪娘器灵 — 人类阅读版

文档用途：给项目开发者和第一次接触本项目的人快速说明“这是什么、为什么这样设计、准备怎样实现”。
当前状态：方案设计、三crate软件地基、v0.2感知契约、双节点桌面状态融合和屏幕ViewModel已经建立；模拟器可连续跑100轮。首批实体硬件已于2026-09-04确认到货，并于2026-09-11完成首轮bring-up：Zero 3W主机系统启动、WiFi与免密SSH远程通道、开机自诊断和显示驱动软件链均已验证通过（空闲0.36–0.41A@5V、温度40.5–46.1°C平台化）；视频链因随附Mini HDMI线DDC通道故障未通过，已换线待复测，屏幕触摸能力亦待确认。逐件身份核验（RAM容量、microSD料号、屏幕型号、环境温度）仍未完成。OCLive主仓已经增加类型化sensor回合来源，本仓已有窄适配器；默认回放仍使用确定性desktop fixture，可操作桌面面板中的真实调用尚待接通。本文中的尺寸、重量、功耗和阈值仍须以实测修正。
更新时间：2026-09-18

一句话：把 OCLive 的角色和状态系统装进一个通用导轨配件，让 wargame 发射器拥有会观察握持、姿态和动作，并用屏幕作出回应的“器灵”。

命名：仓库名是`oclive-四季宝器灵`，正式产品名是`A.I.Live-ai枪娘器灵`。“四季宝器灵 / Skippy Spirit”只保留为灵感来源和早期工程代号；以后新增的程序与协议使用`ailive-gun-spirit`技术前缀。

定位：wargame、收藏、把玩和角色陪伴。不是军用设备，不做弹道、自动瞄准、目标识别或火控；所有传感器只负责观察，任何电子模块故障都不能改变发射器原有机构的工作方式。

首台原型载体：森柏龙 RADIAN MODEL 1 2.0 火控版。电子核心仍按通用皮卡汀尼导轨设计，RADIAN 只负责第一套实体适配验证。

一、当前完整结构

整套系统分成一台主机和两个无线传感节点：

```text
前部摄像头（P1）──隐藏 USB 线──┐
                                 │
前下导轨节点 ─────── BLE ───────┼→ 屏幕主机一体舱
                                 │   Orange Pi + OCLive + 屏幕 + 主电池
后握把节点 ───────── BLE ───────┘
```

1. 屏幕主机一体舱

- Orange Pi Zero 3W 6GB（Allwinner A733）本地运行Linux与OCLive，并把CPU量化3B作为可选角色回复候选。
- 主板通过USB-C DisplayPort Alt Mode主动转HDMI接现有3.5英寸屏；转接器也必须藏入主机舱并实测。
- 3.5 英寸 480×800 HDMI IPS 电容屏，横向按 800×480 使用。
- 主机、屏幕、可充主电池、电源管理和接口都藏在统一外壳内。
- 通过刚性导轨座与 yaw / pitch / roll 三轴摩擦关节调整视角。
- 屏幕边缘有缓冲框；收纳或碰撞时由外壳和缓冲材料承力，LCD、PCB 和电池不承力。

2. 前下导轨节点

- 电子盒安装在较靠后的下导轨位置，不必做成固定前握把。
- 原型使用 XIAO nRF52840 Sense，自带 BLE 和六轴 IMU。
- 可移动前握把或导轨护片内放置 FSR 408 条形压力传感器。
- FSR 通过一根很短的两芯线进入下导轨节点；线可以走现有 M-LOK 开口、护木内部或可更换线槽。
- 这个节点负责前手握持、枪身参考姿态、运动和震动特征。

3. 后握把节点

- 机械上分成薄握把套和握把底部电子盒。
- 薄握把套放置压力传感器，表面增厚目标约 1.5–3 mm。
- 握把底部放置 XIAO、节点电池、开关和充电口，避免整只握把都变粗。
- 只读扳机辅助传感器通过约 20–40 mm 的隐藏短线接入本节点。

4. 前置摄像头（P1）

- 使用 Linux 通用 UVC USB 摄像头，优先 MJPEG。
- 摄像头固定在前端，USB 主线沿护木内部向后走。
- 靠近三轴支架时只露出一小段柔软、可更换的 USB 跳线。
- 摄像头接入屏幕后面的 Orange Pi，不是直接接屏幕。
- 只做 wargame 娱乐观察，不叠加准星、弹道和目标识别。

无线的准确含义是：每个物理区域拥有一个无线节点；区域内部允许几厘米到十几厘米、完全藏入外壳或护木的短线。不是给每一颗传感器分别增加 BLE、电池和配对。

二、五条必须同时设计的链路

1. 信息链路：现实怎样被 OCLive 理解

```text
手掌施压
→ FSR 阻值改变
→ 分压电路产生不同电压
→ XIAO ADC 读取整数
→ 节点固件滤波、校准、去抖和判断
→ BLE SensorObservation
→ Orange Pi 融合前握、后握和 IMU
→ DeviceEvent
→ 器灵状态机 / OCLive
→ visual_state_id + HUD
→ 屏幕反馈
```

OCLive 不应该认识“ADC 大于 2600”这类具体硬件条件。阈值属于节点固件；OCLive 只认识稳定语义，例如：

```text
grip.engaged     已确认握持
grip.released    已确认松开
unknown          节点断连或事实过期，无法判断
motion.raised    已进入举起姿态
trigger.test     只读辅助触发事实
```

这样以后把 FSR 换成电容、光电或别的压力结构，OCLive 主逻辑不需要重写。

第一批状态语义已经确定：

- Held 进入：后握被握住即可成立；只有前握被握住时，还需要枪身正在移动。进入 Held 后，只要任一握持仍成立，即使枪身静止也保持 Held。
- Ready：仍然只有一个 Ready 状态。后握 + 举起是较低/中置信度；前握 + 后握 + 举起是高置信度。这样既支持单手举起，也能识别完整双手握持。
- Standby：只有前后都明确松开，并且枪身持续静止才成立。节点掉线产生的是 unknown，不能当成已经松手。

例如，枪靠在背包上碰巧压住前握 FSR但没有移动，不会直接进入 Held；用户从前部把枪拿起来时，前握和运动一起让它进入 Held；进入后即使用户停下来，只要仍握住就不会睡眠。具体压力、角度、等待秒数和置信度数值仍需要硬件实测。

2. 能源链路：谁给谁供电

系统有三个互相独立的电池域：

```text
P0完整成品5V电源（不拆壳）
→ 受保护的5V分配点
→ Orange Pi、屏幕、USB Hub、P1 摄像头

前节点 1S 小锂电
→ XIAO 电池接口与板载电源系统
→ MCU、IMU、FSR 分压

后节点 1S 小锂电
→ XIAO 电池接口与板载电源系统
→ MCU、FSR、只读扳机传感器
```

电流必须形成回路：从电池正极经过负载，再由 GND 返回电池负极。GND 不是“多余的一根线”，而是电流和信号共同的参考与返回路径。

前后节点通过 BLE 通信，因此不需要和主机共地。摄像头通过 USB 接主机，USB 同时承担 5V 供电、GND 返回和数据通信。

注意：XIAO 的电池接口面向可充锂电。CR2032 是不可充电一次电池，不能接在可能被 USB 充电的路径上。若以后改用 CR2032，必须改为专用低功耗节点和不可充电电源路径。

主机电池先按轻量化路线跑通：

- P0仍以连续4小时实际使用为硬门。旧Zero 2W路线的20.6–29.4Wh估算已经失效；先测Zero 3W、屏幕和本地3B真实占空比，再计算最小电源。
- P0使用完整、不拆壳的成品充电宝/电源，固定输出5V。台架电源建议有5A量程并从较低限流开始验证；旧3A级只能作为测试点，不能预判足够。不能使用诱骗板给Orange Pi输入9V或12V。
- 5 V 分成两条受保护支路，分别给 Orange Pi 和屏幕；不能先供屏幕，再让屏幕顺便给主板供电。
- P0 充电时关机，不先实现边充边用。先记录平均功耗、启动峰值、压降、温升、自动休眠和低电切断行为，再决定 V1 的定制 1S/2S 电池与电源板。
- 首轮台架关机流程是：按关机请求键 → OCLive 保存 → Linux 正常关机 → 指示可以断电 → 用户关闭凹入式主开关。普通充电宝通常不会把内部低电状态告诉 Linux，所以台架不虚构自动欠压关机；field成品必须增加可信低电输入和监督MCU/PMIC/锁存负载开关，在保存完成后真正切断主电源。Linux显示已关机本身不等于电池已经断开。

主机舱的重量、屏幕省电和存储也按“先跑通、实测不足再升级”处理：

- P0 把成品电源、Orange Pi 和屏幕放在同一个移动舱里，保持内部短线和完整外观。先用 225/285/345 g 假体测试；完整移动舱超过 350 g 时，先减电池、外壳和非必要接口，仍不合格才把电池移到固定导轨底座，用一根受控 5 V 软线跨过三轴。
- 屏幕采用正常亮度、降低亮度、关闭背光三级状态；主机、BLE和触摸仍然运行。初始可用30秒无交互降亮、120秒Standby关背光、300ms内唤醒，之后实测调整。候选屏必须真正支持软件控制背光；显示黑画面不等于省掉背光功耗。
- 如果背光管理后仍不能达到4小时，再考虑环境光传感器、CPU/外设低功耗，最后才研究Linux休眠，不提前增加难以恢复的复杂度。
- P0 使用高耐久或工业级MicroSD。角色状态用SQLite事务和checkpoint保存，传感器高频原始值不持续写卡，日志轮转并限制总大小，同时提供角色和配置导出。
- 只有异常断电和磨损测试证明MicroSD不够可靠，才升级USB SSD；只有SSD的体积、功耗和USB占用也不能接受，才重新选择带eMMC的主板。

第五批已经确定节点电池采用可拆硬壳匣，但前后允许两种尺寸：

- 两种电池都使用相同的受保护 1S LiPo 电气规范：标称 3.7 V、充满 4.2 V、相同极性、防呆和电量语义；不要求大小电池匣一定机械互换。
- 前节点先保留 200–260 mAh 候选，后节点保留 120–160 mAh 候选。最终大或小由实测平均电流、8 小时回放后 20% 余量、低温、重连、温升和手感决定。
- 后电池匣预计约 35–38 × 16–20 × 8–10 mm、6–9 g；前电池匣约 36–42 × 22–24 × 8–11 mm、8–12 g，均为 ESTIMATED。可拆结构相对固定软包每节点预计增加 3–6 cm³ 和 2–5 g。
- 电芯、保护板、接点和外壳组成独立匣体，使用非磁性滑轨和卡扣；原型可先用带检修盖的可拆托盘。
- 前后节点都设置凹入式物理硬开关，关机时真正断开电池，适合装包运输。
- 可以借用发射器电池的可拆换体验，但不能使用可误接 7.4/11.1 V 电池的通用 wargame 插头作为节点 1S 入口。

充电按两阶段处理：

- P0 原型直接使用 XIAO 上的 USB-C，兼顾烧录、维护和装机直充。充电时不使用节点，硬开关放在允许电池连接的位置；实际充电时间和温升等硬件到货后实测。
- 电池匣现在就预留非磁性、防反接的正负充电触点和充电座空间，但暂不增加充电座的开发复杂度。
- V1 再制作 USB-C 独立充电座，换下来的大小电池匣都能按同一电气接口充电；定位使用卡槽/适配块，不使用磁吸。

节点怎样知道该换电、怎样安全关机也已经确定：

- 第一版直接使用 XIAO 板载电池电压检测，报告真实毫伏值和 normal / low / critical，不显示看似精确、实际未经校准的百分比。软件和接口为以后增加专用电量计留扩展位置；只有实测证明板载方案不够时才加硬件。
- low 时只提醒；critical 时先关闭原始调试数据和高频日志，继续保留握持、运动结论与 BLE 心跳。到实测关机点后，节点通知 Orange Pi 保存状态，再用保留电量完成受控关机，不能一直耗到保护板突然断电。
- 具体关机电压和余量不靠猜。到货后要在低温、重连峰值和老化电芯下反复测试，保证最差情况下连续 10 次都能完成通知、保存和关机。
- 角色身份、记忆、成长、用户设置和会话摘要保存在 Orange Pi/OCLive；节点只保存自己的身份、配对、校准参数和关机原因。
- 重启时保留角色连续状态和已验证校准，但清空“正在握持、正在移动、Held、Ready”等实时判断，先显示 unknown，拿到新鲜传感数据后再恢复。这里的传感器重置不是重新自动校准，避免用户握着开机时把压力误当成零点。

3. 接口契约：每一段应当怎样连接和表达

契约不只是插头形状，至少包括：

- 机械契约：尺寸、固定方式、插头方向、线长和弯曲半径。
- 电气契约：电压、最大电流、极性、引脚顺序和是否允许热插拔。
- 协议契约：BLE Service、Characteristic、字节格式、sequence 和重连行为。
- 语义契约：`engaged`、`released`、`unknown` 分别意味着什么。
- 时间契约：采样率、去抖时间、TTL、超时和事件冷却。

例如前握节点对外可以报告：

```text
node_uid: 7f...21
boot_id: 4c...09
binding: grip.front
sequence: 1821
observation_type: grip.engaged
confidence: 0.93
battery_mv: 3970
firmware_version: 0.1.0
calibration_version: front-a1
assembly_id: front-assembly-a1
```

BLE 实际可使用紧凑二进制；上面的文本只是帮助人理解语义。

节点登记采用“注册表而不是蓝图”：

- 长按主机维护键才打开约60秒的配对界面，一次只确认一个新节点；具体时间以后按操作实测调整。
- 每个节点与主机拥有自己独立的BLE绑定密钥。增加新节点只是给BlueZ密钥库和白名单各增加一项，删除丢失节点也只撤销这一项，其它节点不用重新配对。
- OCLive节点注册表不保存BLE密钥，只保存永久 `node_uid`、显示名、可信/撤销状态、能力、当前安装位置、固件/schema、装配与校准引用和最后出现时间。
- `node_uid`表示永久设备，不能只用可能变化的BLE地址；`boot_id`每次启动变化；`assembly_id`表示板、传感器和机械夹层这套装配，变化后旧校准失效。
- 安装位置只是对现实的描述，不是理想配件蓝图。系统允许只装后握、缺少前握或以后加入第三方节点；缺失能力只让证据减少或变成unknown，不能让角色包启动失败。
- 角色包只接收DeviceEvent，不知道FSR型号、BLE地址、节点厂商或发射器结构，因此不会把现有配件生态绑死。

BLE传输采用“即时事件 + 当前快照”：

- 握持、松手和运动状态变化立即发送；节点另外约每秒发送一次完整当前状态。即时包偶然丢失时，下一快照会把主机修正回来。
- FSR和IMU在节点内部以较高频率采样和滤波，BLE只发送结论。第一轮可试FSR 25–50 Hz、IMU 26–52 Hz、快照1 Hz和电池30–60秒一次；这些都是到货后修正的估算。
- 原始压力和IMU流只在维护模式低频输出，正常下场不持续上传。
- 断连后旧握持、运动和trigger动作不补发；主机先把事实变成unknown，重连后通过HELLO和新鲜快照恢复。断线期间变化次数可以作为诊断，但不会让角色迟到响应。

“为什么关机”与旧动作不同，它是可以保存的生命周期事实。数据库不写一个模糊的“关机”字符串，而保存结构化记录，例如关机范围、原因、时间、是否正常和是否已经被角色消费。

角色在关机前和恢复后各反馈一次，两阶段分别去重。真正关机时不临时调用AI或网络：系统在正常运行、缓存不足或角色设定更新时，提前生成并校验少量关机/恢复短句；关机时使用近期生成且没有重复的候选，没有合格候选就立刻使用固定兜底。表达缓存不写入角色长期记忆。

角色只看到手动、低电、维护、更新、过热、存储故障、异常重启等标准原因和友好部件名称。数据库错误码、路径、堆栈和硬件日志只给系统诊断，绝不交给角色。系统保存最后一次关机和有界历史；缺少正常关机标记时，下次启动生成一次`unclean_restart`，消费后不反复触发。

IMU不使用一套写死的“标准举枪角度”，而提供类似游戏手柄陀螺仪的用户校准功能：

- 系统坐标统一为向前、向左、向上；节点安装方向通过机械防呆和软件坐标变换适配，换方向后要求重新确认。
- 校准分成传感器静止偏置、安装方向、用户行为三层。用户在向导中自行选择自然放低点和举起点，再做数次自然举起/放下，系统只计算角度范围、过渡和迟滞。
- 第一版可从静止3秒、放低2秒、举起2秒、举放5次开始，全部由实测调整。完成后先显示识别时间线，用户接受才保存；可以取消、回到上一版或重置。
- 同一装配允许多个命名校准档案，适配不同使用者或姿势。档案绑定节点、安装位置和机械装配；换节点、传感器或安装方向后不能静默套用旧档。
- 只有用户进入校准/维护模式才临时录制原始运动数据；平时不后台学习、不持续写卡，避免阈值自己漂移。
- IMU只报告静止、运动、放低、举起和诊断冲击。跌落或震动不翻译成击发，举起也不等于瞄准或Ready；Ready仍需要握持等其它证据。

屏幕交互先采用“触摸负责日常，实体键负责兜底”的简单路线：

- 主机舱设置两个彼此独立、凹入外壳并且不易误触的高阻尼实体键。POWER短按控制背光，长按发起安全关机；MAINT短按返回或完成最小确认，长按请求进入维护界面。
- 屏幕收起贴近枪身、墙面或装包受压时，先由外圈海绵和刚性止挡承力。LCD与按钮都退在保护平面内，海绵不得持续顶住按钮，也不能代替硬限位。
- 运动或Ready时锁定配对、解绑、校准和设置修改；锁定后仍能通过实体键查看提示、返回、控制背光或安全关机。进入维护还要满足静止且非Ready，并使用长按加二次确认。
- 第一版界面让角色表情和反馈占主要区域，只在边缘显示电量、前后节点、网络和模式。电压、RSSI、压力值和版本放在维护页；不显示准星、弹道、目标或射击参数。
- 软件接口会预留未来的“把玩 / 下场”等交互模式，但P0只实现一个角色优先默认模式。以后模式可以改变信息密度、触摸权限和角色主动程度，不能改写底层传感事实或安全关机规则。
- 实体键操作力、长按时间、海绵厚度和戴手套触摸尺寸都还不是定值，必须用装包、贴墙、碰撞假体和戴手套操作实测后冻结。

软件采用两个独立薄核合作，而不是把硬件逻辑塞进OCLive：

```text
传感器与BLE
  → 枪械感知内核：判断“物理上发生了什么”
  → DeviceEvent
  → OCLive内核：判断“角色怎样理解和回复”
  → 屏幕输出
```

- 枪械感知内核是为wargame发射器/枪械交互特化的独立Rust内核，放在本仓，但不依赖OCLive。它管理节点、校准、断线、证据融合、Held/Ready等状态和故障降级。
- OCLive仍然只管理角色包、记忆、情绪、回合和回复，不读取ADC、IMU原始数据、BLE地址或FSR阈值，也不能反过来宣布“现在正在握持”。
- 最外层主机程序同时连接两个内核。感知内核一边输出当前状态快照，供重连、即时画面和诊断使用；一边只在状态真正变化时输出事件，交给OCLive，避免每秒重复触发角色说话。
- 第一版在同一个主机进程内运行，但建立独立感知crate和窄桥接。只有桥接层认识双方并复制必要的值；两个内核不能引用对方、共享内部对象或修改对方状态。
- 这样既获得清晰地基，又不提前制作IPC服务、插件市场、复杂蓝图或多个后台进程。以后确实需要独立崩溃、升级或资源调度，再按实测拆分。
- 当前链路只能观察，不提供波箱、电机、供弹、火控或其它执行控制接口。OCLive失败只失去角色回复，感知与安全关机仍继续；感知失败则相关事实变成unknown，角色不能自己补造事实。

屏幕前端由最外层`ailive-gun-spirit-host`共同编排，而不属于任何一个内核：

```text
感知内核 → 当前状态、低电、断线、维护提示 ─┐
                                              ├→ Output Arbiter → 屏幕
OCLive    → 角色表情、文字和情绪表现 ────────┘
```

- 正常画面以角色为主体；边缘状态栏持续显示电量、节点、网络和模式；安全关机、维护确认、锁定与重要故障使用最高层系统提示。
- 角色回复不能遮住系统提示。回复到得太晚、已经过期或对应的状态已经变化时，仲裁器直接丢弃，不让旧台词覆盖新状态。
- OCLive不可用时，系统状态、维护和安全关机画面继续，并使用本地角色兜底；屏幕渲染重启后根据最新状态重建，不改变感知判断。
- 两个内核都只提供语义，不规定像素、CSS或显示驱动，因此以后更换前端或屏幕不会迫使两个内核一起修改。

模式与输入桥接也由主机外层管理：

- 把玩/下场等模式由用户通过主机UI或实体操作切换。模式可以让角色更活跃或更安静、改变画面信息量，但不能把同一个物理动作解释成另一套传感事实。
- 感知内核以后增加新节点或新事件时，OCLive不用同时升级。只有桥接层明确写出“这个事件需要怎样交给角色”后，它才会进入OCLive；尚未映射的事实仍可显示和诊断。
- 屏幕对拿起、断线、低电等状态立即反馈，不等待AI。只有首次进入Held、Ready等有意义变化才考虑触发角色回复；每秒快照、压力抖动和重复状态不会反复让角色说话。
- 桥接层会对事件去重、短时间合并和设置冷却。具体等待与冷却时长需要通过模拟回放和实际把玩感受确定，当前不写死。

以后增加语音时，感知和主对话仍然保持独立：

- 感知内核永远只报告“用户做了什么、设备现在怎样”，不知道有没有麦克风、用户是否正在讲话，也不输出开心、警惕、紧张等角色情绪。
- OCLive侧的输入调度器负责组合输入。没有语音/文字时，一次有意义的拿起或举起可以作为主要输入，让角色主动回应；有人说话时，语音/文字是主要输入，近期握持、姿态和节点状态只是同一个回合的辅助上下文。
- 角色包可以规定同一个设备事件对这个角色意味着什么，包括情绪倾向、是否主动回应、冷却和把玩/下场模式差异。因此换角色不改传感固件，换传感器也不改角色内核。
- 用户开始说话后，尚未发送的传感器主动回合取消并合并进语音上下文；已经迟到的旧回复通过事件ID、上下文版本和有效期丢弃。语音识别的临时文字不触发回复，最终文字才提交。
- 严重低电、关机和维护确认不属于“谁先说话”的竞争，始终立即显示和处理；角色可以稍后理解友好摘要，但不能延迟保护动作。

语音仍在P0之后。当前只把未来接口边界记录清楚，不采购麦克风、不实现ASR，也不让它阻塞传感器—屏幕—本地OCLive闭环。

输入合并先使用一个很短的等待窗口：传感动作通过门控后先等约500–800毫秒；这时用户开始说话，就把动作并入语音回合，没有说话才让角色主动回应。这个等待不影响屏幕立即亮起、低电提示和安全操作，具体时间以后通过回放调整。

交给主对话的设备上下文保持很小：当前Held/Ready/Standby、模式、节点健康与电量，再加最近约2秒最多4个动作变化和相应时间/置信度。它不是传感日志，不包含原始压力、IMU波形、音频和无限历史。

角色的枪械反应使用单独的“枪械交互伴随包”，而不是OCLive标准角色包字段：

- 标准OCLive角色包继续负责角色本身的人格、记忆、通用Prompt和资产。
- 枪械特化扩展包引用一个基础角色，描述该角色在被拿起、举起、进入不同模式时的情绪倾向、主动回复概率、冷却和表现方式。
- 扩展通过稳定的基础角色身份和版本约束建立关联，不复制人格、记忆、通用Prompt和角色资产。
- 专用加载器只放在四季宝仓库的集成层，让本项目中的OCLive宿主识别这个扩展；OCLive标准加载器和标准角色包格式不需要认识它。
- 扩展包缺失或版本不兼容时，基础角色照常运行，只是不启用枪械专属主动反应，设备事实仍可在用户主动说话时作为普通上下文。

伴随包会保持OCLive熟悉的导入体验，但与角色包彻底分开：用户可在维护页从电脑选择一个目录或压缩包。系统先把它放进临时区，检查格式、版本、文件摘要、大小和路径安全，再安装到`content/gun-interaction-packs/<pack_id>/<version>/`。基础角色包仍在自己的目录里，伴随包用角色ID和版本范围关联它；不会把配置塞回角色目录，也不会直接运行电脑上任意位置的文件。若同一个角色安装了多份枪械伴随包，由本机绑定记录明确选择当前版本。

第一版伴随包只有一份`gun-interaction.json`配置，描述“拿起/举起等事件在不同模式下怎样影响回复概率、冷却、情绪倾向与表情ID”。它不能带程序、脚本、网址、任意文件路径、用户记忆或视觉模型；PNG和未来Live2D仍属于基础OCLive角色包。

文档也按同样原则分仓：四季宝仓库保存感知内核、节点、电源、机械、枪械交互伴随包和硬件HostProfile；OCLive仓库只保存所有宿主都能复用的通用角色、输入调度和资源协调契约。两边可以互相链接，但不能把四季宝的具体阈值、结构和二次开发格式混入OCLive通用规范。

软件地基也已经确定。压力节点先产生强类型SensorObservation，感知内核把多个观察合成带unknown和新鲜度的PerceptionState，只有真正状态转换才生成DeviceEvent。现有v0.1文件只是早期草稿，第一条正式实现基线直接从v0.2开始，不背负无人使用的兼容层。

代码已经从旧启动骨架整理为三个crate：contracts只放这些“接口合同”，perception-core只负责确定性融合和状态机，host负责Linux/BLE/Web、OCLive桥接与伴随包导入。它们第一版仍编译成一个程序，不会因为拆清职责就增加三个后台服务；这样既打好地基，也不提前微服务化。

这些接口合同以后只从Rust类型生成一份JSON Schema，而不是让代码和文档各写一套。可以把它理解成：Rust结构体是源代码，JSON Schema是自动生成的API说明书，CI每次都重新生成并核对；BLE为了省电使用更紧凑的二进制“快递包装”，但拆开后必须得到同一份数据。共享测试样例会检查节点固件和主机对同一串字节的理解完全一致。

前后两个无线节点也不假装拥有同步时钟。每个节点只用自己的启动编号、消息序号和开机后毫秒数排列自己的数据；主机收到时再盖一个主机单调时间戳。比如前节点显示1250 ms、后节点显示900 ms，不代表前节点更晚，因为二者开机时刻不同；主机只根据收到时间、有效期和融合窗口判断它们能否一起作为“当前证据”。这样不需要复杂的无线校时。

状态里的“未知”会成为正式类型，而不是空值。例如后握节点断线后是`unknown(node_offline)`，尚未校准是`unknown(uncalibrated)`，过期是`unknown(stale)`；它们都不等于`released`。最后一次旧读数可以保留在诊断页帮助排错，但不能继续参与握持判断、角色上下文或当前UI。这能从地基上避免“断线后系统一直认为还握着”或“断线被误判成松手”。

已知事实可以带0到1000的“证据强度”，但它不是概率。例如870只表示当前压力、姿态、校准和规则离阈值比较远、判断较稳定，不表示有87%的统计概率。界面只需要说“稳定”“不稳定”或“建议重新校准”。为了知道一次误判是怎么形成的，每个事实最多保留4个小型证据引用，例如前握观察、后握观察和IMU观察；原始压力和IMU数据仍留在有界诊断缓冲，不塞进每个状态快照。

枪械交互伴随包升级时保留旧版本。比如1.0.0正在使用，导入1.1.0后会先验证和安装，再由用户确认切换；若新配置表现不好，可以立刻切回1.0.0。相同版本和相同内容重复导入等同于已经安装；若有人拿同一个版本号放入不同内容，系统会拒绝，而不是偷偷覆盖。当前正在使用的版本不能直接删除。

新旧无线节点连接时会先“对协议版本”。节点列出自己真正支持的版本，主机从双方交集中选最高版本；比如节点支持0.2和0.3、主机只支持0.2，就明确使用0.2。若没有共同版本，维护页仍能看到这个节点，但它不会参与握持和姿态判断。协商后偶尔收到一条未知/损坏消息，只丢弃该条并记录；短时间反复违规才隔离整个节点，阈值等实机和HostProfile确定。

PerceptionState的revision只代表“理解发生变化”，不代表“又收到一条传感数据”。比如压力值从700变成710但仍是稳定握持，revision不增加；从握持变成松开才增加。屏幕重连或健康心跳可以把同一个revision的完整状态再发一次，但不能因此让角色再说一次话。

伴随包的反应规则保持成简单配置表：每个事件先有一条默认规则，不同模式只覆盖少量字段。例如拿起时默认允许主动回复，场地模式把主动概率覆盖为零。合并顺序固定为“默认→当前模式→主机安全和用户上限”，第一版不加入脚本、条件表达式、优先级规则链或任意Prompt。

主动回复的概率由最外层Host/Input Scheduler抽取，不交给感知内核或AI模型。顺序是先确认事件仍有效，再合并模式规则和用户上限，检查冷却，最后才决定是否开启一次传感器主动回合；之后仍要给用户语音让路。测试可以注入固定随机序列，生产环境记录这次为什么通过或跳过。这里的“70%主动概率”和传感器“证据强度700”是两种完全不同的数据，不能混用。

模式可以明确写`active_reply: disabled`。它只表示“不许这个动作主动打断用户”，并不会删除握持事实、系统画面、诊断或用户说话时的设备辅助上下文。基础角色升级后，Host还会重新检查当前伴随包的角色版本范围；不兼容时只停用枪械反应，基础角色照常运行，并让用户明确选择兼容版本，不会自动偷偷换包。

今后要长期守住四条职责：感知内核只报告物理事实；枪械交互伴随包只声明反应策略；Host/Input Scheduler只负责模式、冷却、概率和输入调度；OCLive只负责角色理解与表达。任何新功能如果必须跨越这些边界，都要先说明为什么、有什么替代、会增加什么耦合和怎样回退，并新增一条架构决策，不能因为写起来方便就顺手塞进去。

节点发送一条非法应用消息时不会立刻永久封禁，但也不能无限刷错误。第一版预计采用“单条丢弃并计数；10秒内3条则隔离30秒；连续3次连接都触发后进入protocol_fault、需要维护页确认”的分级处理。超长消息或协商后仍用错误版本可以直接断开本次连接。这里的数字都是ESTIMATED，普通信号差、BLE重传和断连不算协议违规，后续必须用故障注入与实机数据修正。

本机导入的伴随包第一版不强制作者数字签名，但必须有内容清单和SHA-256，并严格检查格式、路径、文件类型、数量与解压大小。摘要只能证明“内容没有被换掉”，不能证明“作者是谁”，界面会明确显示为本地未签名包。因为P0伴随包不允许代码、脚本、网址、任意Prompt、密钥和模型素材，这个边界目前足够；将来接公开市场时再单独设计发布者签名和吊销体系。

已安装版本、活动binding、禁用原因和导入/切换记录保存在A.I.Live Gun Spirit Host自己的SQLite状态库`ailive-gun-spirit-state.db`。它与OCLive聊天、记忆数据库分开，包文件本身保持只读不变。数据库负责事务切换和回滚，维护页只导出过滤后的JSON摘要，不暴露用户电脑上的原始导入绝对路径。

安装文件与写数据库不能真正合成一次操作，所以第一版会给安装器增加一个很小的“施工记录”。从电脑、U盘或其他磁盘选择的包，先复制到设备受管目录里的暂存区，校验完成后才在同一磁盘内瞬间改名成正式版本，再把数据库状态补为已安装；启用这个版本仍是下一步独立确认。若过程中断电，重启后能根据施工记录、目录和摘要判断应该继续、补记完成、禁用缺失版本还是隔离孤立文件，不会把半个包当成已安装。

实机场地配置的SQLite采用WAL+FULL耐久模式，并在待机或维护时受控整理WAL。开发配置可以明确使用较快的NORMAL，但所有发布与拔电测试必须切回实机FULL。运行中备份必须走SQLite的一致性备份方法，不能只复制一个看起来像数据库的主文件。后续要实测每次提交花多久、关机需要留多少时间、存储卡写入量和WAL增长，再调整参数。

诊断数据不会混成一个无限增长的大日志。安装和绑定记录、节点/协议故障、资源/屏幕日志、临时原始传感数据分别限额；当前估算分别是90天或1000条、30天或5000条，原始传感只在用户主动进入维护模式时保留约10分钟或20 MiB，场地模式默认关闭。这些都是ESTIMATED。四季宝Host不复制OCLive的私人对话、原始语音和角色记忆，诊断包也必须由用户主动导出并说明删掉了哪些隐私内容。

重启时采用“该记住的记住，该重新观察的重新观察”。节点白名单、伴随包选择、用户确认的校准和设备设置由Host保存；角色身份、记忆、连续摘要和预生成关机/恢复短句由OCLive自己的数据库保存。Held、Ready、当前握持、姿态、触点、滤波窗口、BLE会话和短期冷却都不恢复，开机后先变成Unknown。以后新增字段若没有先说明由谁拥有、为何保存和如何恢复，默认不允许落盘。

产品低电会分成Low和Critical Reserve两级。Low只降低背光并停掉相机、复杂动画、后台生成等可选负载；Critical阶段停止新安装和新角色回合，用提前准备好的本地关机短句，限时保存OCLive与Host状态并让Linux关机，最后由独立低功耗电源管理器切断主电源。电池保护板只做最后的过放/短路保护。具体关机百分比现在不写死，要根据真实电池、低温、老化和整机峰值反推预留能量。

开机也不会立刻把旧状态续上。Host先恢复文件和数据库，再恢复OCLive角色连续性，然后重连节点并收集一段新鲜稳定数据。第一批数据只用于建立“开机时现实是什么”的基线，不会因为用户握着设备开机就触发一次“刚刚被拿起”；基线完成后的新动作才产生事件。节点没有及时回来时，相关状态保持Unknown、系统进入可见的Degraded，但基础角色和维护界面仍能使用。正常关机或异常重启可以作为一次友好的生命周期上下文给OCLive表达，不会混进枪械感知事件。

v0.2的传感器信息也已经收窄成五种物理观察：握持接触、移动/静止、滤波后的重力方向、只读辅助触点和冲击诊断。节点不直接宣布“已经举枪”或“已经击发”；主机用方向估计和用户校准得到raised/lowered，用前后握与运动证据得到Standby/Held/Ready。节点电量和故障走单独NodeStatus，断线后的unknown由主机产生。

旧状态机中的Active正式移除。载体只有Standby、Held和Ready；按下只读辅助触点时，载体仍然是Ready，只额外记录`control.primary.engaged`。这样能够让角色对动作作出反应，又不会把“触点被碰到”写成“机构已完成动作”。屏幕休眠属于Host省电，不属于枪械感知状态。

第一版DeviceEvent只有六个中性边沿：held进入/退出、ready进入/退出、primary control按下/释放。冲击、节点断线、低电、模式和关机分别进入诊断、状态或SystemCue，不存在`device.triggered`、`weapon.fired`或控制接口。伴随包可以把“held进入”解释成“被主人拿起”，但不能改变底层事实含义。

OCLive里确实有一个Resource Coordinator，但可以把它理解成“餐厅的订位与让座台”，而不是“后厨每个厨师每秒怎样挥刀”的Linux CPU调度器。它能看系统RAM和CPU核心数量，结合任务预估、租约和优先级，决定ASR、TTS、相机分析、复杂动画或后台生成这类可选重任务现在启动、等待还是降级。

它当前不持续读取CPU利用率、频率和温度，也不设置CPU affinity、nice、cgroup或线程上限。因此BLE接收、节点健康、感知融合、安全关机、实体按键和最低限度系统画面必须始终运行，不能因为“资源不够”被它拒绝或抢占。未来如需接入，只由四季宝集成层注册可选重任务，感知内核仍然不依赖OCLive。

Orange Pi的资源预算属于四季宝专用HostProfile，不属于蓝图或枪械角色扩展包。桌面默认值和旧Zero 2W 2GB测量假设都不能直接照搬到Zero 3W 6GB；第一版应分别实测基础闭环、Web/PNG、3B常驻与短句生成的内存、峰值负载和温度，再决定安全余量。

真正移植到Orange Pi之前还要做一次OCLive Linux裁剪审查。这里的“删掉”首先是指不编译、不安装或不随设备镜像发布桌面专用能力，不是直接从OCLive主仓删除源码。审查会把依赖分为四类：角色、记忆、SQLite和无头回合等直接带过去；桌面窗口、生命周期和显示由ailive-gun-spirit-host替换；语音、本地模型、复杂动画等按需启用；Windows/macOS、托盘更新及设备不使用的开发工具不进入镜像。

这不能只凭文件夹名称判断。需要在Orange Pi目标架构上查看Cargo feature依赖树、最终程序链接了哪些动态库、镜像里有哪些文件和systemd服务，并实测每项能力的内存、线程、磁盘、启动时间与离线行为。最终形成一张“保留/替换/可选/排除”表；四季宝继续依赖锁定版本的OCLive，不复制出一份容易分叉的精简内核。

当前资源路线已经确定为：P0只观察资源，不让协调器拒绝或抢占任务；现在建立Orange Pi实机填空表和HostProfile字段骨架，所有数值等硬件到货后填写；P1才把语音、相机分析、复杂renderer等可选重任务接入协调器。轻任务可以留在ailive-gun-spirit-host，带大型原生库、独立模型或不可控线程池的重任务可以拆成systemd服务，最终按实测决定。

软件实施已经正式开始。旧的单package和`oclive-skippy-spirit`二进制已经一次性迁移为三个crate：contracts保存v0.2接口合同，perception-core保存不依赖OCLive的确定性边沿逻辑，host继续承载OCLive无头入口和未来Linux/BLE/Web组合。三份Rust DTO已经能确定性生成SensorObservation、PerceptionState和DeviceEvent v0.2 Schema，并有3个有效、6个无效样例以及零漂移测试。

第一批感知测试已经固定几个重要行为：开机第一批数据只建基线不发事件，Unknown不被猜成松手或新动作，同一个revision只能重发完全相同的快照，revision倒退或同号内容变化会被拒绝，Held进入Ready只产生ready边沿，只读primary control不修改carrier状态。已经可以运行`ailive-gun-spirit-sim`在Windows命令行回放拿起、举起、辅助触点、重启、放低、待机和Unknown，并查看JSON事件。完整SensorObservation多节点融合、BLE协议、OCLive桥接、屏幕UI和伴随包安装仍未完成，所以现在是“地基和生命周期回放已可测试”，不是完整器灵闭环已完成。

硬件到货填写包已经整理到仓库`docs/test-worksheets`并复制到桌面。包内按到货清点、主机/屏幕、无线节点、电源/关机、机械/场地五组提供空白表；Orange Pi详细系统门继续使用`ORANGE_PI_BRINGUP_WORKSHEET.md`。桌面副本可现场填写，完成后应把文档和照片/日志证据交回仓库，再用MEASURED数据更新阈值、功耗、包络和ADR。

这不是照着OCLive重新做一个“硬件版调度器”。通用Resource Coordinator仍直接复用OCLive实现；四季宝只补充这块板子的预算、任务估算和降级方式。枪械感知内核模仿的是OCLive薄核的职责分离与稳定契约，不是模仿资源调度器。需要现场填写的完整表格见仓库`docs/ORANGE_PI_BRINGUP_WORKSHEET.md`。

资源诊断采用“现场看摘要，回家看证据”的组合：维护页显示内存、温度、节点、网络、存储健康和最近故障等少量信息；后台日志保持有界并轮转，用户明确操作后才能导出包含版本、近期资源快照和生命周期记录的完整诊断包。默认不导出角色私密对话、原始音频和持续原始传感流，低存储或关机时诊断导出不能阻塞系统保护。

设备分development与field两套HostProfile。开发配置允许详细日志、维护原始流和测试接口；场地配置关闭这些非必要能力并收紧资源/功耗策略。两套配置共享板卡基线、安全边界和schema，分别做启动、断网、关机冒烟，并维护明确差异清单。它们是部署配置，不是角色的把玩/下场interaction_mode；切换后通过受控重启生效。renderer边界按下一段的同进程可拆方案执行。

屏幕renderer第一版留在ailive-gun-spirit-host同一个进程，但不直接嵌入Output Arbiter。双方通过一个可拆的RendererPort传递“最新完整画面”，通道只保留最新revision；屏幕画得慢时跳过旧画面，不把感知和安全链路堵住。触摸以单独UiIntent返回host，旧触摸不在重启后补发，实体POWER/MAINT不依赖屏幕程序。

这只是提前保留拆分能力，不是假装已经拥有进程隔离。实机测试会注入慢渲染、绘制错误、task退出、损坏资产和触摸洪泛，并记录画面p95、host内存/线程、两小时增长、恢复时间、温度和是否影响感知。如果renderer导致host崩溃、长阻塞、OOM、资源无法回收，或者以后引入Chromium/大型原生图形库、需要单独更新，就改用独立systemd renderer；没有这些证据则继续同进程。

屏幕界面采用Web路线，以Vue/TypeScript/HTML/CSS实现800×480角色舞台、状态栏、维护页和触摸，并为以后接入Live2D WebGL保留空间。P0仍只要求PNG表情、短文字和HUD；具体使用哪种Linux浏览器/WebView不在纸面决定，要在Orange Pi上比较启动、内存/线程、磁盘、WebGL、触摸、温度和两小时稳定性。WebGL或模型失败时必须自动回到PNG和系统状态画面。

Host只发送语义资产引用，不发送任意路径或每帧像素。普通表情引用经过校验的PNG资产ID；Live2D引用一个带版本和内容摘要的完整模型bundle，模型、纹理、动作等内部文件只能在受控目录内解析。缺失、版本不符、摘要错误或路径越界都拒绝加载并使用默认PNG。

Host负责当前页面、模式、配置锁、配对、校准、解绑、关机和操作是否成功；Web renderer只负责滚动、按钮反馈、页面过渡和Live2D动画混合。比如用户点击“开始校准”，页面必须等Host确认设备静止且未Ready后才能进入下一步；renderer重建时校准进度恢复，但动画从头播放没有关系。

Live2D是P1可选表现，不成为P0启动依赖。开发验证和公开发行是两件事：若以后允许角色生态加载多个第三方模型，发布前必须重新检查当时Live2D SDK与可扩展应用许可，角色模型自身授权也要独立确认。

屏幕消息第一版采用“最新完整画面”，不传差量补丁：每次都包含当前角色区、状态栏、系统Overlay和交互页面以及递增revision。屏幕画得慢时直接跳到最新revision；仍有效的短动作带唯一ID和截止时间留在当前画面里，过期就不补演。页面刷新或renderer重建后只拿最新快照，因此不需要依赖旧消息历史。

Vue页面由仅本机loopback HTTP提供，ViewModel与UiIntent走WebSocket。这不是外部服务器，也不允许局域网控制。即使只在localhost，本地其它进程仍不能默认可信：场地Profile只绑定本机，禁止通配CORS、远程页面和开发服务器，并校验Host、Origin、启动会话、消息大小/频率、sequence与页面revision。网页只能申请白名单操作，Host仍按当前锁和状态重新判断；实体关机键不经过网页。

视觉资产直接复用OCLive已经存在的portrait catalog、visual_state_id和visual presentation。PNG与未来Live2D模型仍属于基础角色资产；枪械交互包只选择“拿起时更倾向哪个表情/动作”，不复制模型。四季宝验证相对路径和catalog闭集后生成运行态AssetRef。以后若大型模型确实需要独立下载，可以给AssetResolver增加Visual Pack来源，不必改双内核、Output Arbiter或现有ViewModel。

本轮坚持先跑通：P0只做PNG、短文字、HUD、维护页、最新快照恢复和安全触摸，不实现Live2D、独立视觉包、差量协议、可靠动画队列或远程控制。RendererPort和AssetResolver保留替换接口，但不提前制作没有调用者的实现。

第四批 FSR 电气接口已经确定：

- 第一版使用简单分压把 FSR 阻值变成 ADC 电压，不增加运放或带旋钮比较器模块；47 kΩ 只是起始试验值。
- 前后 FSR 都通过藏在节点盒里的微型两针防呆连接器接入，连接器两侧做应变释放，使传感握片可以单独更换。
- 在传感器远端预留一颗可选 EOL 高阻电阻的位置。正常松手时它产生一个很小的基准电压，短线或插头开路时 ADC 接近零，从而比基础分压更容易区分故障。
- EOL 阻值暂不冻结；台架比较未安装和不同高阻值后决定。它只帮助识别开路，不能独自识别线路短路、外套持续预压或 ADC 卡高。
- 不默认直接焊接 FSR 柔性尾片，实际采用传感器厂商允许的焊片、压接或夹持方式。

4. 故障链路：坏掉时怎样安全降级

- FSR 抖动：节点本地滤波、迟滞和时间防抖，不把原始噪声交给 OCLive。
- 节点断连：相关事实进入 `unknown`，不能永远保留断连前的“正在握持”。
- 数据重复或乱序：通过 `node_uid + boot_id + sequence` 去重，过期事件丢弃。
- 节点低电：报告 normal / low / critical；先停非必要数据，到实测关机点后通知主机保存并受控关机，低电期间仍保留关键状态。
- 主机低电：先提示，再保存必要状态并正常关机，避免直接损坏文件系统。
- 屏幕或主机崩溃：watchdog 重启；不影响发射器原机构。
- 扳机传感器损坏：只丢失观察能力，不改变扳机行程、电机、火控或供弹。

基础 FSR 分压可能把“真正松手”和“FSR 导线断开”都表现为低电压，因此 V0 在传感器远端预留 EOL 电阻。是否安装及阻值由 released/open/engaged 三类台架数据决定；若仍不能可靠区分，主机把事实标成 unknown，而不是假装已经松手。

5. 机械链路：力和线缆怎样经过结构

前握区域：

```text
手掌
→ 外层握把套 / 力扩散片
→ FSR
→ 刚性背板
→ 握把或导轨结构
```

压力不能传到电池、PCB 或焊点。传感器需要感受力，电子器件则需要避开主要受力路径。

第二批 FSR 机械方向已经确定：

- 前部把“可移动传感握片”和“后方下导轨电子盒”分开。前握只携带 FSR 与受力层，XIAO、IMU 和电池留在后方节点盒，中间使用一根局部隐藏短线。
- 后握第一版只在原握把后背带放一条纵向 FSR。先做 100 次握持测试；若左右手、手套或不同握法存在明显盲区，再增加左右双侧传感器。
- 后握从外到内是：薄可拆外套 → 力扩散片 → FSR → 原握把。扩散片位于 FSR 上方，原握把本身就是刚性背板，不需要打开握把再塞硬板。
- FSR 尾线沿握把套隐藏线槽进入可拆底盒；底盒不能遮死原电机底板、检修和通风位置。

例如掌心偏左压住握把时，扩散片会轻微弯曲，把局部压力传给中间的 FSR。扩散片太软会漏检，太硬或外套太紧会产生持续预压，因此材料与厚度仍由实测决定。V0 全部采用可拆结构，不钻孔、不切削、不永久粘接原握把。

第三批验证与校准规则也已确定：

- 第一阶段做 100 次握持—释放：右手裸手、右手手套、左手裸手、左手手套各 25 次，混合轻握、正常握和较紧握。
- 再做 50 次开机负样本，例如静置、轻触、拿取底盒、枪身移动但没有握后把。正常装包、运输和长期收纳直接整机关机，因此不要求系统在背包持续挤压下保持开机判断。
- 单条 FSR 需要总成功率至少 95%，每个分组至少 90%，50 次负样本最多误判 1 次，并且不能存在一种固定握法总是漏检。未通过时先调整机械和校准，仍失败才升级双侧。
- 每个装配保存基础校准；更换 FSR、扩散片或握把套后旧校准失效。平时直接加载，识别不好时可从屏幕明确启动一次用户校准。
- 开机时不能自动把当前压力当作零点，因为用户可能正握住设备；必须加载保存值，只有用户明确要求时才重新标定。

屏幕区域：

```text
外部碰撞
→ 泡棉 / 保护片支撑区
→ 主机舱骨架
→ roll 关节
→ pitch 关节
→ yaw 关节
→ 刚性导轨夹具
```

LCD、Orange Pi 和电芯都不应该成为结构件。

摄像头线缆：

```text
前端摄像头
→ 护木内固定主线
→ 固定应变释放点
→ 可更换短 USB 跳线
→ 三轴服务弧
→ 主机 USB 口
```

硬限位必须在线缆被拉紧之前生效。第一版至少做 500 次全角度循环检查，之后把 1,000 次作为结构验收目标。

三、当前重量与体积预估

当前 Orange Pi + 3.5 英寸 HDMI 完整目标原型预计增加约 330–520 g，中心值先按约 400 g 设计。按 RADIAN 商品标称 1.76 kg 计算，完成后约 2.09–2.28 kg；必须用用户手中的实物重新称重，因为商品重量可能不包含相同附件和电池状态。

| 部分 | 预计重量 |
|------|----------|
| 屏幕、Orange Pi、主电池、供电、散热和一体外壳 | 225–345 g |
| 三轴关节与导轨夹具 | 45–80 g |
| 前节点 | 18–28 g |
| 后节点 | 20–30 g |
| P1 摄像头、外壳、线缆 | 20–35 g |
| 完整增加重量 | 约 330–520 g |

主机舱初步包络：约 100 × 65 × 30–38 mm。三轴支架折叠包络约 70 × 35 × 25 mm。前节点约 65–80 × 24–26 × 9–11 mm；后握底部电子盒约 34–38 × 28–32 × 13–16 mm。

这些尺寸是设计盒，不是成品承诺。真正影响手感的是质量离握持中心的距离：同样的重量越靠前、越远离握持中心，手腕力矩越大。因此主机舱优先靠近机匣和握持中心，只有轻量摄像头位于前端。

当前减重触发线：

- 移动主机舱超过 350 g：停止放大关节，先减电池、接口和外壳，或切换紧凑屏幕/主板路线。
- 完整套件超过 520 g：当前形态否决，必须重新做重量分配。
- 4 小时续航所需电池让主机舱厚度超过约 40 mm：重新评估平均功耗、屏幕背光、紧凑 DSI/HDMI 屏或分体电池，不直接接受“背一块大盒子”。

四、功耗和电池为什么必须实测

当前仅作计算占位：

- P0基础闭环（不加载3B、不含摄像头）平均功耗暂按4.5–7W、峰值按10–15W准备。
- P0加入间歇3B短句后平均功耗暂按5.5–9W，真实值取决于角色回复占空比；峰值按12–18W准备。
- P1加入UVC/只读视觉后平均功耗暂按6–11W。
- 假设转换效率 85%、只使用电池标称能量的 80%。

由此得到：

```text
P0基础闭环运行4小时：约需要26.5–41.2Wh标称能量
P0含间歇3B运行4小时：约需要32.4–52.9Wh标称能量
P1含UVC/只读视觉运行4小时：约需要35.3–64.7Wh标称能量
```

这些是宽区间`ESTIMATED`，只用于准备台架和暴露“持续本地推理可能增大电池”的风险，不能直接拿上限去堆电池。硬件到货后必须分别测量：关屏、四档亮度、Wi-Fi、BLE、OCLive、3B未加载/常驻/短句/连续压力、USB触摸和UVC；用真实场地回复占空比计算平均值。没有实测前不冻结mAh、1S/2S和电芯尺寸。

五、实现顺序

阶段 0：先冻结契约和软件模拟

1. 扩展 SensorObservation 的节点电源类型，加入 `lipo_1s`。
2. 明确前、后节点 `node_id`、BLE 服务、字段、单位和 TTL。
3. 用 Windows mock 模拟前握、后握、举起、断连和低电。
4. 验证 DeviceEvent、器灵状态机和屏幕反馈，不接真实硬件。

阶段 1：主机与屏幕

1. Orange Pi 使用桌面限流电源启动。
2. 点亮 HDMI 屏，识别 USB 触摸。
3. 本地运行 OCLive，完成自启动、日志、watchdog 和断网降级。
4. 连续运行两小时并记录功耗、温度、内存和画面延迟。

阶段 2：前下导轨节点

1. XIAO 先用 USB 供电读取 FSR 原始值。
2. 确定分压电阻、采样率、滤波、握持和释放阈值。
3. 通过 BLE 把 `grip.engaged/released` 交给主机。
4. 加入板载 IMU，输出移动、静止和举起事实。
5. 最后才接受保护 1S LiPo，测充电、温升、重连和续航。

阶段 3：后握把节点

1. 复用前节点相同的 BLE 核心和固件，只改变 `node_id` 与配置。
2. 先做后握 FSR，再做握把套和底部电子盒。
3. 最后增加独立、只读的扳机辅助传感器。

阶段 4：两节点融合

1. 前握、后握和固定 IMU 共同判断 Standby / Held / Ready。
2. 模拟节点断连、数据重复、低电和传感器卡死。
3. 完成两小时台架闭环后才冻结节点外壳。

阶段 5：机械假体和上枪验证

1. 用 225 / 285 / 345 g 三档主机舱假体测试三轴手感。
2. 做前后节点等尺寸假体，检查握持、操作和拆装净空。
3. 先断电装配，确认没有干涉原机构。
4. 再做通电静态测试和至少三次场地 Alpha。

阶段 6：摄像头 P1

1. P0 闭环通过后接入 UVC MJPEG 640×480 / 30 fps。
2. 实测端到端延迟、CPU、温度、功耗和掉帧。
3. 完成三轴短跳线 500 / 1,000 次循环和拉力缓解测试。

七、2026-08-27 开工前工程审查结果

这次审查不只是“看看代码”，而是把软件契约、Cargo工作区、验证门禁、硬件路线文档和后续接手规则一起核对了一遍。

已经修好的问题：

1. 三crate不再只是文档说法。Cargo原先会自动把vendor烟测库也算成workspace成员，现在已经明确排除，并用脚本检查成员和依赖方向。
2. 相同revision重发现在允许“分类语义不变、发布时间和同值证据时效刷新”。以前心跳或1 Hz新鲜快照会被误判成内容冲突；现在它们会延长TTL，但不会制造新动作或角色回合。
3. 感知回放入口会先校验状态；非法Fact不能再悄悄建立启动baseline。
4. 节点、boot、observation和event ID改成受校验构造，空ID/超长ID更早被拒绝。
5. 生产路径中的expect已经收敛为Result；严格Clippy已经成为门禁。
6. 屏幕、节点、无线和电池专题文档已全部回到当前路线：Orange Pi + 3.5英寸HDMI、前后双BLE节点、受保护可充1S LiPo。Lyra+DSI只保留为紧凑回退，CR2032只保留给未来专用低功耗节点。
7. 三crate迁移后的ARMv7 Host已经重新交叉编译成功：22.19 MiB、ELF32 ARM EABI5 hard-float。它证明代码能生成对应ABI，仍不代表Lyra实机的内存、屏幕和无线通过。
8. 模拟器不再直接填写Held/Ready答案，而是模拟前、后两个节点发送SensorObservation，再由感知内核自己处理节点身份、boot、sequence、TTL、举放校准、Standby等待窗和Unknown降级。
9. Host已经有最小Input Scheduler、DeviceContext和Output Arbiter：事件先形成明确的sensor输入请求，桌面角色夹具给出测试RoleCue，系统故障提示可以抢占角色层，旧RoleCue不能覆盖新状态。
10. 标准序列已经自动连续跑100轮，每轮都验证能回到Standby，节点超时后屏幕进入System提示层；这证明桌面状态链不会轻易卡死，但不是实体传感准确率证据。

以后完整软件审查只需在仓库根运行：

```powershell
./scripts/verify.ps1
```

它会检查三个包的格式、依赖边界、Clippy、全部测试目标、doctest、Schema漂移和Rust依赖漏洞。不能再用cargo fmt --all，因为它会越过本仓去检查兄弟OCLive。

需要实机的内容没有被假装解决：Orange Pi内存/温度/显示、触摸、Wi-Fi/BLE共存、节点续航、FSR阈值、IMU校准、主机四小时、电池关机、三轴力矩、整枪重量和场地误判，继续等硬件到货后按桌面测试包填写。

当前真正的下一软件任务分成两条：本仓继续做NodeHello/BLE golden vectors和可操作的PNG/Web测试界面；兄弟OCLive主仓先增加兼容的类型化sensor回合来源和副作用策略，再由本仓窄桥接替换`desktop_fixture`。现在不能把DeviceEvent拼成一段伪用户文字去调用OCLive，因为那会污染聊天、记忆、好感或人格边界。

九、P1+余弹估算扩展：循环短计数与磁浮板互相校正

这项功能已经确定设计方向，但不进入当前P0，也没有经过实物验证。它会在传感器—OCLive—屏幕主线和场地Alpha通过后，作为独立弹匣配件继续开发。

它不依靠单一传感器：

```text
发射器每完成一次可信机械循环
    → 短计数减去一颗的估算量
    → 让画面中的余量连续变化

枪身停稳，弹匣套重新读取霍尔阵列
    → 确认水弹大致位于满、3/4、1/2、1/4或低余量
    → 校正短计数的累计误差
```

发射循环能够准确记录“机械完成了多少圈”，但空击、卡弹或供弹失败时不一定真的消耗水弹。因此界面第一版只承诺“满、约四分之三、约一半、约四分之一、低余量、无法确认”，不把内部估算颗数宣传成绝对真实。

每次获得可信霍尔范围后，程序都会建立一个新锚点并把“从锚点开始的短计数”清零。运动和射击时主要依靠短计数；再次停稳后再用霍尔收窄范围。两种结果差异过大时显示“需要确认”，而不是偷偷选择一个看起来更漂亮的数字。

机械结构分两类：

1. 散装电动水弹弹匣候选使用接近弹仓截面的半圆/D形低重心浮板。左右两侧的留量结构是连续导向，负责防止浮板旋转和进入供弹口，不能做成会把浮板卡在几个固定高度的档点。浮板侧面密封一颗小磁铁，电子霍尔阵列放在外部弹匣套中。
2. 弹簧供弹弹匣不另做浮板，而是在原有托弹板后面隐藏一个很小的磁铁座；托弹板本身就会随余量移动，位置关系更直接。

散装弹匣目前有一个必须通过实物解决的问题：如果水弹从顶部倒入，整片浮板可能挡住新水弹或被埋在下面。需要根据原装弹匣的加弹口决定是装填时把浮板停靠顶部、从浮板下方侧装，还是放弃整片浮板。没有拆解尺寸前不能把它当成已经解决。

发射循环优先从火控已有的循环传感器读取；如果火控没有可用输出，再看电动回膛是否与波箱一比一，或增加独立只读霍尔/光电观察。未知火控电平不能直接接XIAO，必须先测电压、共地和波形，并使用高阻缓冲或电气隔离。任何检测方案坏掉时都只能失去余量显示，不能影响扳机、电机、火控或供弹。

详细实现、未来契约、故障降级和实测顺序单独保存在`docs/MAGAZINE_AMMO_ESTIMATION.md`，硬件到手后填写`docs/test-worksheets/07-余弹融合与弹匣结构测试表.md`。这两份属于四季宝器灵仓库，不写进OCLive主项目文档。

十、2026-08-28 OCLive传感回合接通与前端准备

现在传感器事件不再需要伪装成“用户说了一句话”才能进入OCLive。兄弟OCLive仓已经增加三种明确来源：user、sensor和system；普通桌面/HTTP聊天仍自动属于user，外部请求不能自己选择“不留记录”的来源。

sensor回合可以读取角色和近期上下文、生成角色回复和立绘状态，但不会把这次动作写成用户聊天，也不会修改长期记忆、事件、好感、关系、人格、连续性或虚拟时间；它也不会把设备事实送进用户情绪分析器。自动测试已经验证：同一会话先运行sensor回合，所有这些状态保持不变；随后运行普通user回合，原有聊天和角色情绪写入仍正常。

本仓的OcliveSensorAdapter是两个内核唯一相遇的位置。它把有界DeviceContext写成机器可读的中性事实，以类型化sensor来源调用OCLive，再把reply和visual_state_id转换成RoleCue交给Output Arbiter。感知内核仍不知道角色，OCLive仍不知道FSR、IMU、BLE节点和枪械阈值。

前端可以从现在开始画。入口文档为FRONTEND_DESIGN_BRIEF.md：

1. 先用800×480横屏画布，四周24 px暂定安全区；样屏到货后按真实边框、海绵和视角修正。
2. 只画RoleStage、StatusBar和最高优先级SystemOverlay三层。
3. 第一轮准备Booting、Standby、Held、Ready、Primary Control、节点离线、未校准、低电和关机九张状态稿。
4. 可以先比较“角色舞台+相机状态框”“纯角色侧屏”“战术HUD”三个低保真方向，不必立刻画精稿。
5. 3.5英寸屏幕上的44–48 px触控目标物理尺寸太小，首轮按约80 px准备；常用和危险操作仍优先实体键。
6. 当前模拟器输出中的screen_view_model就是前端数据样例，页面不自行伪造后端字段。

当前完成的是来源契约和真实窄调用能力；默认命令行回放仍用desktop_fixture，方便没有本地模型时做确定测试。下一步是把真实OCLive调用接进可操作的桌面面板，并加入PNG/Web画面、超时、取消、迟到回复和时延测量；完成这些以后才能称为完整桌面纵向闭环。

十一、终端机外观与背部散热方向

终端机外观确定为一台以3.5英寸横屏为核心的微缩三防数据平板：正面屏幕下沉在保护边框内，哑光黑的相机半笼式金属框夹住四角和上下边，背面使用蜂窝装甲纹路，主体深空黑、辅助战术灰，只用少量荧光黄作为识别线和标识。正式文字使用“A.I.LIVE // GUN SPIRIT”和“SPIRIT CORE”，不再把旧SKIPPY作为新Logo；系统是低压设备，也不印不真实的“HIGH VOLTAGE”。

内部按三层排列：

```text
正面：屏幕、透明保护片和半笼
中间：短HDMI/USB、可拆主板托盘、主板和安装在开发板SoC上的散热器/小风扇
背面：带流线型局部让位凹槽的一体蜂窝防护后盖
```

小风扇不是独立的机箱风扇层，而是直接安装在开发板散热器上。外面的一体蜂窝后盖负责保护和导流，内侧用流线型小凹槽避开主板、接头和散热组件，使外壳贴近硬件但不接触或挤压器件。具体风扇多大、向里吸还是向外吹、是否PWM温控，等主板和屏幕到货后测温再决定。电池不能挡住主风道；它在底边、侧边还是后盖非热区，继续按完整厚度、温升、重心和四小时续航选择。

背面又可能在收纳时贴近枪身，所以蜂窝不能只在完全敞开时才能散热。四角泡棉下面还要有刚性止挡，并在背面中央留下空气间隙；侧边也要有真实进出风口。这样贴枪后不会把风扇完全堵死。蜂窝孔还必须防止手指、挂绳、泡棉或软包装碰到扇叶。

到货后会分别测试裸板、被动散热、风扇开启、贴枪收纳、蜂窝局部遮挡和风扇停转。风扇坏掉时系统应先降低复杂画面和后台任务，继续显示必要状态并允许安全关机。详细结构记录在`docs/TERMINAL_ENCLOSURE_VISUAL_V0_1.md`，原始温度和功耗填写主机与屏幕测试表。

十二、Zero 3W 6GB与本地3B角色短句

主机板已经从Orange Pi Zero 2W 2GB改为Orange Pi Zero 3W 6GB/A733。它仍是约Zero级长条小板，但有2个A76性能核、6个A55效率核和6GB LPDDR5，更适合同时运行OCLive、屏幕界面与本地小模型。代价是现有HDMI屏需要增加USB-C DP主动转HDMI件，而且新SoC的Linux、GPU/NPU、功耗和散热都必须重新实测，不能继承旧板结论。

3B模型最适合本项目的不是长篇推理，而是短、情绪强、事实范围窄的角色台词。例如“喵！！！！！！！”、“你让你的家族蒙羞！”、“队友呢队友呢救一下啊”。OCLive仍掌握角色、关系、记忆和当前事实，3B只负责把这一轮写成角色会说的话；这样比让3B独立维护全部人格可靠得多。

但“内存放得下”和“说得又好又快”是两回事。当前预计3B Q4短句约3–5 token/s，只用于准备测试，不是实测承诺。短句可能几秒完成，长角色上下文和长回复会明显变慢。因此未来语音分两层：要求时机的“喵！、自己人、急救”等先用预生成/缓存语音立即播放；3B可以稍后生成不重复的补充句，再交给独立TTS发声。P0仍先完成屏幕，不提前增加扬声器和语音链。

受伤、队友、危险接近等台词只有在游戏状态、用户输入或未来明确的只读事件提供事实时才能触发；现有握持和IMU不会自行猜测。详细的模型、量化、速度档位、固定台词语料和质量评分入口在`docs/LOCAL_3B_INFERENCE.md`，原始数据填`docs/ORANGE_PI_BRINGUP_WORKSHEET.md`。

板子到货后不会只测3B。现在确定用同一套对话和角色样例比较三个代表尺寸档：约3B、1.5–1.7B、0.5–0.6B。先测未经训练的量化模型，再给它们加入相同的精简角色资料、已确认事实、少量相关台词和近期记忆。这样可以看清楚究竟是模型太小、角色资料没有取对、说话风格不够，还是单纯速度太慢。

如果问题只是“不像这个角色”，才在电脑显卡或云端做LoRA训练；Orange Pi只负责运行训练完成并量化后的模型。如果小模型LoRA仍然不够，而且已经积累了稳定、人工筛选的数据，再评审0.5–0.6B全量微调。最终不要求整台设备只能运行一个尺寸：立即喊声继续走审核语音池，简单动作短句可以由小模型处理，需要关系和记忆组合的短对话再交给较大模型或网络模型。

十三、硬件已经到货以后怎样开始

2026-09-04已经确认首批硬件到货，但工程上“包裹到了”和“器件已经验证”是两件事。现在先不把所有东西接起来，而是把每件硬件拍照、记录丝印和卖家链接，确认输入电压、接口方向、是否破损，再从Orange Pi单板开始。

固定顺序是：主板单独启动，随后单独确认屏幕供电，再加入视频转接、触摸、最低界面；然后分别测试前节点和后节点，最后才做双节点、电池、外壳和上枪。每一步只增加一个变量，这样故障出现时知道是新加入的哪一段，不会面对“一整套都不工作”却无从判断。

项目文档也重新建立了入口。`docs/README.md`负责告诉人和AI应读什么；`PROJECT_BASELINE.md`说明现在从哪里出发、怎样才算硬件闭环完成；`PROJECT_BOUNDARIES.md`说明四季宝、OCLive和角色资产各自负责什么；`HARDWARE_ENGINEERING_GUIDE.md`用于边学边做。桌面里的旧四季宝文件没有删除，但仓库版是唯一继续修改的版本，旧副本不能反向覆盖。

边界保持简单：P0只做外挂导轨角色终端、两个无线感知节点、本地Host/OCLive和屏幕。语音、相机、Live2D、余弹和更多节点以后再评审；自动瞄准、目标识别/跟踪、弹道、火控和原机构控制不属于本项目。OCLive内核还在梳理，四季宝暂时只保留接口契约，不急着推进跨仓真实调用。当前第一件实际工作只是填写硬件到货清单，不接电池、不进波箱、不上枪。
